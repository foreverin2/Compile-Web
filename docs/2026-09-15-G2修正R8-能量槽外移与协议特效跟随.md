## §2 R8-2 + R8-3：能量槽移出链路框 + 横置向左 + 链路预留七张

### §2.1 目标层级：一列七层，**DOM 顺序即视觉顺序**

```
.net-lane-band（一列）
├─ .net-side.net-side-foe
│  ├─ .battery              ← 层 1：对手能量槽（横置）
│  ├─ .stack-slot           ← 层 2：对手链路（虚线框；框内只有 .stack）
│  └─ .protocol-cell        ← 层 3：对手协议
├─ .net-lane-mid            ← 中线
└─ .net-side.net-side-self
   ├─ .protocol-cell        ← 层 4：自己协议
   ├─ .stack-slot           ← 层 5：自己链路
   └─ .battery              ← 层 6：自己能量槽（横置）
```

**关键变化：能量槽不再是 `.stack-slot` 的子节点，也不再靠 CSS `order` 决定落端。**
`.net-side` 是 flex column ⇒ **DOM 兄弟顺序 = 视觉上下顺序**，两侧镜像由挂载顺序表达。

**为什么这是净收益（不是"换个写法"）**：R1/R-F 的两轮 Critical（C-2）全部出在
"能量槽的落端由 `.stack-slot` 内的 CSS `order` 决定"，而 `order` 的选择器一旦从
**按侧**（`.net-side-foe/.net-side-self`）写成**按绝对玩家号**（`.p1/.p2`），默认席位下
两个能量槽会一起跑到内侧 —— 那时守卫还是绿的。移出后**这个自由度消失了**：
`order` 一退役，"哪一层在哪"只剩 DOM 顺序一个出处。

### §2.2 `renderStackSlot` 新增 `withBattery?: boolean`

`renderStackSlot`（`render.ts:223`）目前无条件 `slot.appendChild(renderBattery(...))`（`:345`）。

- 新增 `opts.withBattery?: boolean`，**默认 `true`** ⇒ 热座页逐字等价（构造性不变）。
- 远程页传 `withBattery: false`，然后在 `renderSide` 里**自己**调 `renderBattery(s, player, line)`
  并挂到 `.net-side` 的对应端。

**为什么不"先挂进去再搬出来"**：那会留下 12 个 `.battery`（6 个 display:none 的死 DOM），
`NET_PAGE_HOOKS` 的 `.battery` 计数与"产出链条"会同时失真，正是"守卫表达不了行为"的老坑。

### §2.3 ⚠️ 承重项：能量槽节点自带 `data-player` / `data-line`，6 个 FX 定位点一起迁移

**这是本任务唯一会"静默杀死既有特效"的地方，必须先读这一段。**

现状：能量槽在 `.stack-slot` 内，于是**所有**定位它的 FX 都写成
`.stack-slot[data-player="X"][data-line="Y"] .battery-shell`（`.battery` 自己**没有** data 属性）：

| `src/ui/render.ts:441` | 扫描流光 `syncScanOverlays` |

   `batteryNode` 同理取 `.battery`）。
3. 迁移后**必须逐条变异实测**：把 `.battery[data-player=` 改回 `.stack-slot[data-player=`，

> 热座页的 DOM 因此多了两个 data 属性。这是**有意为之**的取舍：换来"能量槽与位置解耦"。
> 既有的"热座零变化"红线**只针对朝向/特效标记**（`data-fx-rot` / `orient`），不针对

### §2.5 R8-3：链路预留 7 张牌（竖向）

**现状**：`.net-lane-band .stack`（`styles-net.css:199`）只给变量，**没有高度**；
高度由内容决定 ⇒ 每放一张牌，`.stack-slot`（虚线框）就变高，整块棋盘跟着抖。

**尺寸推导**（沿用文件里已有的"名义基准"口径，不引入新魔法数）：
- `--card-h: 182px`、`--card-w = (182 − 2) × 0.71429 + 2 ≈ 130.57px`（现状，不动）；
- 相邻两张卡的步距 = 卡高 + 负 `margin-top` = `var(--card-h) + (0.462 × var(--card-w) − var(--card-h))`
  = **`0.462 × var(--card-w)` ≈ 60.3px**；
- **7 张的跨度 = `var(--card-h) + 6 × 0.462 × var(--card-w)` ≈ 543.9px`**。

**改法**：把 `--card-h` / `--card-w` 的定义从 `.net-lane-band .stack` **上提到 `.net-lane-band`**
（`.stack` 仍继承得到，值不变），然后：

```css
.net-lane-band .stack { min-height: calc(var(--card-h) + 6 * 0.462 * var(--card-w)); }
```

**连带效应（必须一起改，否则方向会反）**：`.stack` 一旦有了 `min-height`，
内容不足 7 张时就有**自由空间** ⇒ 原先被注释判定为"惰性（死）CSS"的两条
`justify-content` **变成承重**（`styles-net.css:217-224` 的那段注释要改写）：

- `.grow-down`（自己，DOM `[最旧 … 最新]`）配 `flex-start` ⇒ `pos 0`（最旧）贴顶部
  （= 贴自己协议 / 中线），越新的越往下 ⇒ **自己向下生长** ✓
- `.grow-up`（对手，DOM `[最新 … 最旧]`）配 `flex-end` ⇒ `pos 0`（最旧）贴底部
  （= 贴对手协议 / 中线），越新的越往上 ⇒ **对手向上生长** ✓

两者共同语义仍是"`pos 0` 贴协议、越新的越向外"。**若把这两条写成同值，方向必反** ——
这正是 R-F2 · I-3 踩过的坑，所以 §5 的 G-3 要把它钉住。

**注意**：`.stack-slot` 自身 `justify-content: center`（来自 `styles.css:69`）此后
不再有自由空间（内容恒 ≥ `min-height`），是惰性的 —— 不必改，但**不要**指望它摆方向。

**整块棋盘的后果（用户已明确要求）**：三条线 × 两侧 × 543.9px ≈ 纵向 1100px 起，
加上协议与能量槽 ⇒ 棋盘显著"变窄变长"（与用户 R1 的原话一致），需要滚动。

## §3 R8-4：协议特效跟随 ∓90° 旋转

### §3.1 现象与根因

远程页协议图（`styles-net.css:293-294`）靠**图片自己的** `transform: rotate(∓90deg)` 横躺
（自己 `.net-rot-ccw` / 对手 `.net-rot-cw`），**但协议相关的 FX 全都按"未旋转的 100×140 竖版盒"
建盒定位**：

1. **已编译协议持久 FX 层**（`render.ts` `buildCompiledFx` / `positionCompiledFxLayer:1520`）：
   层是 body 级 `position: fixed`，每帧按 **holder 的 `getBoundingClientRect()`** 覆写
   `left/top/width/height`。holder 是**未旋转**的 100×140，而协议视觉盒是 **140×100**
   ⇒ 环/角光/藤蔓/裂纹全部贴着"一个竖版框"画，与横躺的协议**错位 90°**。
2. **编译翻面浮层**（`effects/index.ts:1907` `playProtocolFlip`）：`wrap` 用
   `.protocol`（= holder 盒）的 rect ⇒ 同样是一个 100×140 竖版浮层盖在 140×100 的协议上，
   而且 `rotateY` 的翻转轴也就落在了错误的轴上。
3. **重排协议幽灵**（`effects/index.ts:2286` `playRearrangeProtocolsFx`）：rect 取自
   `.protocol-img` 的 `getBoundingClientRect()`（**这个已经是旋转后的视觉盒** ✓），
   但幽灵内部的图与 `rot180` 判定仍按"竖版"给 —— 需按同一标记归一。

> 用户说"**所有协议**的特效"，对应的就是第 1 条：每个已编译协议都常驻一组装饰，
> 90° 错位在**每一组**上都成立。

### §3.2 标记落点：`.protocol-holder` 上的 `data-fx-rot`

沿用 R1/R2 已经建立的两套朝向机制（**卡面**朝向 vs **特效**朝向），协议这一侧补齐特效腿：

- `renderProtocol`（`render.ts:94`）新增末位可选参数 `fxRot?: 'cw' | 'ccw'`；
  **给了才写** `holder.dataset.fxRot = fxRot`（与 `renderStackSlot` 的 `fxRot` 同款守卫，
  默认 `undefined` ⇒ 热座页 DOM **一个字节都不多**）。
- `renderProtocolCell`（`render.ts:2003`）新增末位可选参数并透传。
- `render-net.ts` 的 `renderSide`（`:714`）传 `isSelfSeat ? 'ccw' : 'cw'` ——
  **与同一处给协议的 `net-rot-ccw/cw` 同源**，两处不可能脱钩。

**为什么选 holder 而不是 `.protocol-img`**：`positionCompiledFxLayer(defId, holder)` 的入参
**就是 holder** ⇒ 读侧零祖先查找（DOM 桩不保证实现 `closest`）；且 `.protocol-img` 的
`parentElement` 也是 holder ⇒ 三处 FX 都能直接拿到。

**为什么必须是"只读 `data-fx-rot`、不回退 `orientOf`"的新助手**：
`fxOrientOf` 在标记缺失时会回退 `orientOf`，而**热座页的 P2 协议图本身就是 `.rot-180`**
（`render.ts:141`）⇒ 用 `fxOrientOf` 会把热座页的 FX 层转 180°（**热座红线**）。
故新增纯函数（`fx-orient.ts`）：

```ts
/** 只读 `data-fx-rot`（`ccw` → −90、`cw` → +90）；**读不到或不认识 ⇒ 0（不旋转）**。
 *  与 `fxOrientOf` 的区别：**不回退** `orientOf` —— 用于"把 body 级 FX 层搬到协议的
 *  **视觉**盒上"的场合（热座页没有标记，回退成 180° 会把热座页的层转坏）。 */
export function fxRotDegOf(node: { getAttribute(n: string): string | null } | null): 0 | 90 | -90;
```

### §3.3 三处几何跟随

1. **`positionCompiledFxLayer`**（`render.ts:1520`）：读 holder 的标记，
   `fx.style.transform = deg === 0 ? '' : \`rotate(${deg}deg)\``（`transform-origin` 保持默认
   `50% 50%` —— 层盒与图片**同心**：holder 100×140，旋转的 img 也以同一中心转 ⇒
   层绕自身中心转 ∓90° 后，视觉盒 = 140×100 **与协议视觉盒完全重合**）。
   - 幂等：`img.load` 回调与每帧 `syncCompiledFxLayers` 写同一个值。

### §8.2 已与用户确认的目标排布（`ask_user_question`，用户选 A）

```
[对手信息块一行：信息 · 牌库 · 弃牌堆]      ← 最上

[三条链路 + 控制轨]
```

### §8.3 R8-5/R8-7 机制：`.net-board` 五行网格 + `display: contents`

**硬约束**：`.hand` 的 **DOM 顺序恒为 `[P0, P1]`**（约束 7：FX 用 `querySelectorAll('.hand')[player]`
**按下标**读手牌）。所以**不能**把对手的手牌搬进一个 DOM 位置更靠前的容器 —— 那会让下标 0
变成对手的手牌，**全部手牌 FX 静默错位**。

⇒ 做法：**DOM 一个字不改**，只改 CSS：

- `.net-board` 从 flex column 改成 **grid**（单列多行）；
- `.net-bottom` 与 `.net-hands` 都设 `display: contents` —— 它们的盒子消失，子节点**直接成为
  `.net-board` 的 grid item**（DOM 结构、类名、`data-*` 全保留 ⇒ 既有结构守卫一条都不用改）；
- 用 `grid-row` 显式指派五行，**按侧**（不按绝对玩家号）：
  `row1 = .net-info-block[data-net-seat='foe']`、`row2 = .net-hand-area-foe`、`row3 = .net-grid`、
  `row4 = .net-hand-area-self`、`row5 = .net-info-block[data-net-seat='self']`、`row6 = 日志/诊断/工具条`。
- 手牌区/信息块要**整行**（`grid-column: 1 / -1`）且内容水平中置。
- ⚠️ **`display: contents` 是承重的**：少写一条，那一块就退回"跟着 DOM 顺序走"，视觉顺序**静默**
  变回旧样（而 `grid-row` 声明还在，看着像生效了）。§8.6 的 G-7 必须把这条钉住。
- `@media (max-width: 1180px)` 那段"三列挤手牌"的取舍**前提已消失**（信息块不再与手牌同行），
  必须重新判断：能删就删，保留就要写清它现在还解决什么问题。**不要**留下一条无效的媒体查询。

### §8.4 R8-6 控制轨归中

`.net-grid > .control-module` 的 `align-self: start` → **`center`**。两侧链路等高（§2.5 的 7 张预留后

### §8.5 R8-8 操作按钮只在操作方

现状（`render-net.ts`）：

- `renderInfoBlock` 里 `if (isSelf) block.appendChild(renderNetActionBar(s, cb))` —— **行动区恒挂自己那侧**，
  而 `renderNetActionBar` 内部取 `getLegalActions(s, s.turnPlayer)` ⇒ **对手回合时，我的信息块里显示的是
  对手的「下一步 / 编译线N / 结算触发 / 清理缓存」**，点下去等于替对手走棋。
- `renderChoiceUi` 的三个分支（select / select-line / select-action，以及 `choiceBar(...)` 的产物）都把
  `.choice-bar`（确认 / 跳过）`wrap.appendChild(...)`；`.choice-bar` 在 `styles.css` 是
  `position: fixed; left: 50%; bottom: 18px` ⇒ **视口底部居中**，与"谁在操作"无关，看上去就是"挂在我这边"。

改法：

1. **行动区**挂到**当前回合玩家**那一侧的信息块：`if (player === s.turnPlayer) block.appendChild(renderNetActionBar(s, cb))`。
2. **选择条**挂到**操作方**（`who = prompt.chooser ?? top.player`）那一侧的信息块
   （`.net-info-block[data-player="${who}"]`；`renderInfoBlock` 已经在算 `operator === player`，可复用）。
   远程页的 `.choice-bar` 必须是**流内**的：`position: static; left: auto; bottom: auto; transform: none`
   （与既有的 `.net-action-bar` 同款；`styles.css` 一行不动）。
3. **非操作方那一侧不显示任何操作按钮** —— 这是用户这句话的字面判据，也是本轮唯一的判据。
4. 定向选牌浮层（`buildChoicePickOverlay`，模态、自带无按钮）**不动**；它的"确认/跳过"就是第 2 条的
   `.choice-bar`。它内部那句"选好后点底部「确认」"的文案在远程页会指向操作方那一侧的信息块 ——
   若读起来别扭，改成"点「确认」"即可（**文案属于可改项**）。

⚠️ **不做的**：不加权限、不防作弊（用户明确「不需要对局防作弊」）。"对手那一侧的按钮在本机也可点"
仍然成立 —— 旧实现在**错误的**一侧同样可点，故本轮不构成新风险；但真联机下应由**会话层忽略

## §13.3 R9-1：**一个数（`--card-h`）驱动全部**的等比缩放

**推导表（必须在 CSS 里**推导**出来，不许出现第二组字面量）**：

| 量 | 表达式 | 值 |
| --- | --- | --- |
| `--card-h` | 唯一旋钮 | **140px** |
| `--card-w` | `calc((var(--card-h) - 2px) * 0.71429 + 2px)` | 100.57px |

## §16 R10 / R11 的前三项（R10-2 · R11-1 · R11-4）—— 用户第四次验收里的"小而致命"那三条

用户第四次验收（2026-09-15 晚，逐字见 §17.0）一共交了 4 件事。其中"场上的卡根本没缩小""链路宽度会变"
两条是**用户实机发现、而当时四道门全绿**的缺陷 —— 它们同属"**模型与浏览器级联不是一回事**"那一族。
本节只记这三条**非结构性**的（结构性那条见 §17）。

### §16.1 R10-2：宿主级联把场上卡尺寸吃掉了（用户："场上的卡根本没缩小"）

**症状**：R9-1 把 `--card-h` 从 182 缩到 140，声明读起来完全正确，而实机上场上卡**一点没变**。

**根因（两处叠加，缺一不可）**：

1. `styles.css:422` 的 `.stack { --card-h: 175px; --card-w: calc(…) }` 是声明在 **`.stack` 元素自己身上**的；
2. 自定义属性**只在该元素没有自己的声明时才继承** ⇒ R8-3/R9-1 把 `--card-h` "上提"到祖先
   （`.net-lane-band` / `.net-board`）之后，**祖先上的值永远赢不了元素自己的那条**。

⇒ 场上卡一直按 175 派生（`≈125.57`），而所有守卫解的都是**样式表里哪条声明生效**——
**没有一条守卫能看见"浏览器实际用的是哪个值"**（本仓的简式解析器只做级联解算，不做自定义属性的
元素自身优先判定；那条 175 甚至不在 `styles-net.css` 里，而在热座样式表里）。

**修法**：`.net-lane-band .stack { --card-h: inherit }`（(0,2,0) 压过 `.stack` 的 (0,1,0)，
`inherit` 走浏览器语义取父级的值）。⚠️ 只用 `inherit`、**不写第二个字面量** ——
`net-r9.test.ts` 的 G-10b 专门禁止"第二组独立绝对长度"，写 `--card-h: 140px` 会立刻红。
**连带**：`net-css-parse.ts` 的 `cssVarOf` 必须按浏览器语义处理 CSS 全局关键字
（`inherit`/`unset` ⇒ **继续往祖先找**，`initial`/`revert` ⇒ 返回 null），否则 G-3/G-10a 假红。

### §16.2 R11-1：空链路宽度为 0 ⇒ 放第一张牌时列宽会跳

**症状**（用户）："链路宽度会变"—— 空 `.stack` 的内容宽是 0，`.stack-slot` 的宽 = 内容 + padding；
放上第一张卡后 track（`max-content`）当场变宽，三条列的水平位置随之跳动。

**修法**：`.net-lane-band .stack { min-width: var(--card-w) }` —— 空链路也预留**一张卡**的宽。

### §16.3 R11-4（本轮**顺手抓到**的潜在缺陷）：`.choice-mode` 一直加在**对手信息块**上

`renderNetBoard` 里原本写的是：

```
const hands = bottom.lastElementChild as HTMLElement;   // 注释还写着"手牌区恒是最后一个子节点"
```

而 DOM 顺序由 `NET_BOTTOM_SIDES = ['self','foe']` 决定 ⇒ 实际是
**`[自己信息块, 手牌区, 对手信息块]`** ⇒ `lastElementChild` 拿到的是**对手信息块**。
于是 `.choice-mode`（"选择模式下非候选手牌不可点"的**唯一**出处）加错了节点，
两条消费规则（`styles-net.css` 的 `.net-hands.choice-mode …` 与 `styles.css:1786` 的
`.hand-strip.choice-mode …`）**同时失效**。规则级后果被 render.ts 的 promptId 闸门兜住了
（拖拽打牌仍被拦），所以它长期没被发现 —— 这正是"降级但可玩"掩盖静默缺陷的典型。

**修法**：`buildBottomRow` 返回 `{ row, hands }`，把节点**从构建点直接交出去**，不再靠位置猜。
守卫：`tests/ui/net-dock.test.ts` 的 **G-15a**（行为腿：真跑一帧后 `.net-hands` 必须带 `.choice-mode`、
两块信息块都不带）+ **G-15b**（源码腿：不许再出现 `lastElementChild`）。

### §19.2 R13-1（本波最重的一条）：协议编译特效的**层盒尺寸基准**

**症状**（用户："协议边框没有缩小"）：`positionCompiledFxLayer` 把 body 级持久层盒写成 holder 的**实测**
76.9×107.7，而 `.compiled-fx-*` 的装饰是**按 200×280 用 px 写死**的（`.lava-seg` 14×5 /
`offset-path: inset(-5px round 15px)` / `.compiled-ring` 圆角 14px / 金属护角 54×54 …，
见 `styles.css` 594-624 与 4642-4662）⇒ **盒子缩了、里面的装饰没缩**（相对卡面放大 ~2.6 倍）。

**修法**（`render.ts`）：层盒固定回**作者基准** `COMPILED_FX_BASIS_W/H = 200/280`、**居中**对齐到 holder 的
实测中心，再把整层 `transform: rotate(∓90deg) scale(k)`（`k = 实测 holder 宽 / 200`）。
均匀 `scale` 与 `rotate` **可交换**，合并成一个 transform 不改变几何。
⚠️ **热座零变化**：热座 holder 就是 200×280 ⇒ `k = 1`、`deg = 0` ⇒ 内联 transform 仍是**空串**、
left/top 仍是 holder 左上角。
⚠️ 200 是**两处真相**（另一处在装饰的 px 里）⇒ `protocol-fx-rot.test.ts` 的 **G-13** 从 `styles.css` 的
`.protocol-img { width: 200px }` **解出**这个数与常量比对（改一处忘另一处立刻红）。
`verifyPageHooks` 的**约束 10** 同步放宽成"严格匹配 `rotate(∓90deg) scale(k)` 两段形态"。

### §20.3 本轮两条最贵的方法论教训（**都写进了源码注释**）

1. **"判据与产出共享同一个错误假设"会造出必然绿的假守卫。**
   R15-3 的第一版把 `.protocol-check` 当成**随卡旋转**的元素，于是用 ∓90° 逆映射反推盒坐标，
   并为"两套朝向"各写一条规则（`top: −2.80` / `96.64`）。两条硬事实推翻它：
   （a）`renderProtocol` 把徽标挂成 `.protocol` 的**直接子节点**、`holder` 的**兄弟**
   （`render.ts:183-194`），而 `rotate(∓90deg)` 只加在 `img.protocol-img` 上 —— **transform 不继承**；
   （b）远程页 `.protocol` 被 `.net-lane-band .protocol { padding: 0; border: none }` 清成零内边距，
   它的包含块**就是** holder 盒 `76.93×107.688`（第一版按热座的 `p = 5px` 推出 `86.93×117.69`）。
   实测把第一版的数代回屏幕坐标：徽标中心落到 `(3.58, 4.12)`，而卡视觉足迹是
   `x∈[−15.38, 92.31]`、`y∈[15.38, 92.31]` ⇒ 徽标在卡**上方偏左**，**比修前更糟**；而它的
   "独立重算"腿照样绿，因为测试侧抄了同一个假设。**正确解**（闭式，已写进 CSS 注释）：
   记 `k = --card-h / 182`（徽标边长 `18k`）、视觉足迹右缘 `(w+h)/2`、上缘 `(h−w)/2`，
   内缩取热座同构的 `(11k, 9k)` ⇒
   `left = (w+h)/2 − 20k = 0.54946·--card-h`（≈ holder 宽，是**推导结果**而非巧合）、
   `top = (h−w)/2 = 0.10985·--card-h`（徽标上缘与卡视觉上缘**齐平**）；
   ⇒ **一条与朝向无关的规则**（两套朝向的视觉足迹完全重合），`data-net-rot` 随之成为零消费属性而删除。
   教训：**"这个元素会不会跟着转"必须先读产出方（谁 append 到谁），不能靠观感推断**。
2. **大文件改写不要用 PowerShell。** `Get-Content`（数组）→ 切片 → `Set-Content -NoNewline`
   会把数组元素**首尾相接、一个分隔符都不加**地写出 ⇒ `styles-net.css` 从 **1111 行塌成 68 行**
   （L1 = 35,329 字符、L68 = 20,236 字符、44 条规则粘在一行、`}\n` 出现 0 次），
   而花括号仍 142/142 配平 ⇒ **不会报错、只会静默毁掉行结构**（注释即文档的结构、以及所有
   "行首锚定"的守卫）。恢复：以 `git show HEAD:` 为基底 + 逐条插回语义改动；**验证**：把两份文件
   **剥掉全部空白**逐字符比对 ⇒ 公共前缀 35,161 + 公共后缀 15,577，只剩一段 197/226 字符的差异
   （一处注释更正）⇒ 语义零丢失。**本仓纪律再加一条：修改 >200 行的文件一律用 Node 脚本 +

出现在链路框内侧"）保持不变。**
