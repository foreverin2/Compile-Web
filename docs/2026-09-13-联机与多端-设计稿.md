## §0 本稿范围

### 0.1 要设计什么

把当前"单机热座"的游戏，扩展成一个**本地优先、无后端、可跨端联机**的产品：

- 引擎**确定性化**（同一串操作在任意设备上得到同一结果）
- 一套**档案格式**，同时充当存档 / 录像 / 重连凭据 / 联机传输内容
- **会话层**：把"操作从哪来"收口，支持本地 / 录像 / 联机 / AI 四种驱动
- **传输层**：房间码建房与加入、握手、操作同步、断线重连
- **远程对战页面**（重做，不复用热座页）
- **本地优先的登录与存储**（游客模式 / 用户模式）
- **多端打包与更新**（网页 / PWA / Tauri / Capacitor）

### 0.2 不设计什么

不做服务端权威校验，不做防作弊，不做大厅 / 匹配 / 排位 / 云存档。**单人 AI（§7）与 3/4 人联机留待后续阶段（§11）**。理由见 §12。

### 0.3 已锁定的裁决

| # | 议题 | 裁决 | 影响 |
|---|---|---|---|
| 1 | "无后端"的底线 | 允许一个**不存任何数据**的极轻信令/中继服务（只转发、断开即忘） | 决定了"随时随地联机"的可达上限 |
| 2 | 公平性等级 | **信任制**：不管客户端篡改代码作弊 | 排除了"权威主机 + 视图遮蔽"方案 |
| 3 | 远程对战页面布局 | **甲读法**：3 条横带，每条带内 上=对手 / 下=自己；卡牌仍竖摆 | 见 §6 |
| 4 | 本地下载形态 | **先做 PWA**，Tauri 留作后续可选的壳 | 见 §8 |
| 5 | 联机人数 | **先只做 2 人**；3/4/单人以后考虑 | `PlayerId = 0 \| 1` 保持不变 |
| 6 | 对手如何相遇 | **只做熟人房间码**，不做公开匹配 | 无大厅、无房间列表 |

### 0.4 三条红线

1. **任何服务器都不存储卡组、昵称、个人信息、对局数据。**
2. **不做服务端权威校验。**
3. **游客模式下零写入磁盘**（刷新或关闭即全丢）。

## §1 总架构

### 1.1 分层

```
┌─ src/core ───────────── 纯规则引擎（无 DOM，现有 8.7k 行）──────────────┐
│  本稿只加两件事：                                                       │
│    · createGame({ seed })      种子进状态                               │
│    · s.rng / s.nextUid         随机源与 uid 计数器进状态                │
│  规则、效果、触发、编译：一行逻辑都不改                                  │
└─────────────────────────────────────────────────────────────────────────┘
        ▲ 状态 + 操作指令
        │
┌─ src/app（新增）───────── 会话层：操作从哪来、到哪去 ────────────────────┐
│  MatchDriver 接口 → LocalDriver / ReplayDriver / AiDriver / NetDriver    │
│  ActionLog（操作日志） · MatchFile（档案） · stateFingerprint（指纹）    │
│  settling（动作序列化门）                                                │
└─────────────────────────────────────────────────────────────────────────┘
        ▲ 状态变化 + 事件
        │
┌─ src/net（新增）───────── 传输层：可替换，不碰游戏逻辑 ──────────────────┐
│  Signal（信令：房间码/握手）  Peer（WebRTC DataChannel）                 │
│  Reconnect（重连）           Chat（表情/心跳）                           │
└─────────────────────────────────────────────────────────────────────────┘
        ▲
        │
┌─ src/ui ───────────────── 表现层（现有 26.6k 行）──────────────────────┐
│  热座页（render.ts）保留不动                                            │
│  新增 render-net.ts（远程对战页，甲读法）                               │
│  新增屏幕：授权弹窗 / 建房加入 / 等待对手                               │
│  特效层（fx-*.ts / compiled-gen3.ts）**尽量零改动**，靠 §6.3 的 DOM 契约 │
└─────────────────────────────────────────────────────────────────────────┘
```

**依赖方向严格单向**：`ui → app → core`，`net` 被 `app` 调用且**不反向依赖 ui**。`core` 永远不知道联机存在。

> **关于"core 不改"的准确表述**：规则、效果、触发、编译逻辑**确实不改**。**唯一例外是回合计时的超时判负**（§14.3 已裁决的组合方案）：需要一个能设置 `s.winner` 的操作，因此 `core/game.ts` 新增一个 `'forfeit'` 操作类型 —— 这是本设计**唯一**触碰 `src/core` 的地方，清单与守卫注意事项见 §14.7。

### 1.2 为什么是锁步（方案对比存档）

| 方案 | 代价 | 结论 |
|---|---|---|
| **① 锁步：两边都跑引擎，只同步操作** | 需要先把引擎确定性化 | **采用**。特效天然两边同步（见下）、重连/录像/存档免费 |
| ② 权威主机 + 视图遮蔽 | 要写视图投影层；特效要从状态差异重建；重连要发快照 | 弃。它唯一的优势是防客户端窥牌，而裁决 #2 已放弃防作弊 |
| ③ 全状态快照同步 | 泄漏全部隐藏信息；且"状态被替换"推不出"该播哪个特效" | 弃 |

**锁步在本项目的决定性优势**：现有特效系统是**事件总线驱动**的（`src/core/events/bus.ts` 的 `gameBus`，handler 在 `executeAction` 期间同步执行）。只要两台设备对同一操作跑出同样的状态转移，**事件序列就相同，特效就自动在两边正确播放**，不需要为联机写任何特效同步代码。方案②③都会摧毁这个性质。

### 1.3 现有资产盘点（本稿建立在这些事实之上）

| 资产 | 位置 | 对本次工作的意义 |
|---|---|---|
| `GameState` 是（几乎）纯 JSON 数据 | `core/models/types.ts:327` | 无 Map/Set/类实例；**但 `pendingEffects[].gen` 是活的 Generator**（`types.ts:237`，由 `resolve.ts:223` 的 `pe.gen.next()` 驱动）→ **只有效果栈空时状态才可序列化**。存档与重连按 §3 走"种子 + 操作重放"，不依赖中途快照，因此不受影响 |

## §2 确定性内核（G0）

### 2.1 目标不变式

> **给定 `seed` 与操作序列 `[a₁…aₙ]`，`GameState` 的指纹必须唯一确定，且与执行设备、执行次数、是否中途存盘恢复、模块加载历史全部无关。**

这是锁步的全部前提。达不到它，联机一定会在某一局出现"两边不一样"，而且几乎无法调试。

### 2.2 必须消除的六处不确定性

| # | 位置 | 现状 | 处理 |
|---|---|---|---|
| 1 | `core/engine/deck.ts:11` | 洗牌 Fisher-Yates 用 `Math.random` | 改走 `shuffle(s, arr)`，用种子随机源 |
| 2 | `core/state/create.ts:8` | `let uidCounter = 0` **模块级全局**，uid 取决于进程历史 | 挪进状态：`s.nextUid`，`nextUid(s)` |
| 3 | `core/effects/resolve.ts:668`、`cards/fear.ts:99`、`cards/lust.ts:51`、`cards/time.ts:120` | 四处"随机抽一张"用 `Math.random` | 统一走 `randInt(s, n)` |
| 4 | `main.ts:499`、`ui/home.ts:93`、`ui/home.ts:361` | **掷硬币定先手**与**随机协议池**在 UI 层随机（三处均为 UI 侧 Fisher-Yates / 硬币） | 搬进引擎，由种子派生（§2.5）。**注**：`main.ts:499` 与 `home.ts:93` 的具体归属需在 G0 逐一确认 |
| 5 | `core/trace.ts:34,41` | `Date.now()`（诊断） | 无害，但必须排除在指纹之外；同时审计 `pushLog` 是否写入时间 |
| 6 | `core/effects/context.ts:5-9` | `let effectIdCounter = 0` **模块级全局** —— 第 2 条的孪生，原稿漏记（G0 Task 7 评审发现） | 挪进状态：`s.nextEffectId`，`nextEffectId(s)` |

第 2 条与第 6 条最隐蔽：它们不会在任何单局测试里暴露，因为单进程内计数是单调的。只有"两个进程各跑一遍同样的操作"才会露出来 —— 这正是 §2.7 测试台要专门覆盖的场景。第 6 条更狠：它生成的是 `PendingEffect.id`，联机时两端开局前历史不同就会让 prompt id 对不上号。

### 2.3 种子与随机源

新增 `src/core/rng.ts`：

```ts
/** 随机源状态：进 GameState，因此进指纹 */
export interface RngState {
  seed: string;   // 建房方生成，如 base32(16 bytes)
  n: number;      // 已消耗次数，单调递增
}

/** 原地推进 r.n，返回 [0,1) 的确定性数值 */
export function rngNext(r: RngState): number;

/** 返回 [0, bound) 的整数。bound <= 0 时返回 0（防御） */
export function randInt(s: GameState, bound: number): number;

/** 从数组中确定性取一个（替换现有四处 Math.random 取牌） */
export function randPick<T>(s: GameState, arr: readonly T[]): T | undefined;

/** 确定性洗牌（替换 deck.ts:8 的 shuffle） */
export function shuffleWith<T>(s: GameState, arr: readonly T[]): T[];
```

实现要求：

- 只用**整数运算**（`Math.imul`、`>>>`、位运算）。浮点乘加在不同引擎理论上一致，但整数方案不留任何解释空间。
- 禁止使用 `Math.random`、`Date.now`、`performance.now`、`crypto.getRandomValues`。
- `rngNext` **必须原地推进** `r.n`。若把随机源放在状态之外，则"中途存盘再恢复"会得到不同的后续随机序列，违反 §2.1。

### 2.4 uid 分配

- `GameState` 新增 `nextUid: number`，初值 1。
- `nextUid(s)` → `c${s.nextUid++}`，保持现有格式（`create.ts:11` 现在是 `c1`、`c2`…），避免波及既有测试与存档兼容。
- **改动面**：所有 `nextUid()` 调用点需补 `s` 参数。这是纯机械改动，`tsc` 会全部报出来。

### 2.5 开场随机搬进引擎

现状：`ui/home.ts:361` 掷硬币（`Math.random() < 0.5`）、`main.ts:499` 随机池抽 12 套（UI 侧 Fisher-Yates）。

设计：

- `createGame({ seed, draftStarter?, firstToPlay?, draftMode? })`
- `draftStarter` 未显式给出时**由种子派生**：`draftStarter = randInt(s, 2)`
- `firstToPlay` 按既有规则派生：`firstToPlay = 1 - draftStarter`（"后选协议者先出牌"）
- 随机池模式开启时，`draftPool` 也由种子派生（12 套）
- **UI 的硬币动画改为"演算表演"**：结果已由引擎确定，动画只是把它演出来。视觉零变化，但两边必然一致。
- `MatchFile.setup` 记录这三个字段，保证重放时不需要种子以外的任何外部输入。

> 待核实项（G0 任务）：`tests/state/coin-order.test.ts` 现有断言可能假设硬币在 UI 层，需一并迁移。

### 2.6 状态指纹

新增 `src/core/fingerprint.ts`：

```ts
/** 稳定序列化：对象键排序、数组保序、排除诊断字段 */
export function stableStringify(v: unknown): string;

/** 状态指纹，用于测试台与联机校验 */
export function stateFingerprint(s: GameState): string;
```

- **`s.log` 纳入指纹，不设排除清单**：已核实 `pushLog`（`core/log.ts:17-20`）只做缩进拼接、**不写任何时间戳**，因此日志是确定性的，纳入只会更严格。`core/trace.ts` 的诊断数据不得进入 `GameState`。
- 哈希算法用同步的 FNV-1a 64 位（分两段 32 位拼装）。信任制下不需要密码学强度，只需要**开发期能抓到不一致**。
- **已知盲点（裁决：接受并写明）**：`pendingEffects[].gen` 是活的 `Generator`，`Object.keys(generator)` 为 `[]` → 它在指纹里恒为 `{}`，**挂起效果的内部进度不进指纹**。真正的保障是效果每执行一步都会 `pushLog`、而 `log` 已纳入指纹；D4（12 个种子各跑两遍 + 60 个种子录制-重放）提供整局层面的证据 —— 但注意**两次确定性重跑发现不了两次共有的盲点**。
- **`undefined` 语义已与 JSON 对齐**：值为 `undefined` 的键被省略（与 `JSON.stringify` 一致），故引擎里 `rigidity.ts` 那种显式赋 `undefined` 的形态不再破坏"往返后指纹不变"。**数组元素为 `undefined` 的情形不在覆盖内**（`[undefined]` 与 `[null]` 仍不可区分；当前 `src/core` 不可达，记录为已知限制）。

### 2.7 确定性测试台

新增 `tests/determinism/`，建在现有 `tests/fuzz/lib.ts` 之上。四条不变式：

| 不变式 | 做法 | 抓什么 |
|---|---|---|
| D1 重放一致 | 同种子 + 同操作序列跑两遍，指纹相同 | 基础确定性 |
| D2 存盘恢复一致 | **仅在安全点**（`pendingEffects`/`pendingPlay`/`pendingShift` 全空）才 `JSON.parse(JSON.stringify(s))` 后继续，指纹与 D1 相同 | 状态是否自足（随机源未进状态会在这里失败）。**不能每步往返**：`pendingEffects[].gen` 是活 Generator，序列化即失效 |
| D3 **跨进程一致** | `vi.resetModules()` 后动态 `import` 全新模块实例，跑同样操作，指纹相同 | **模块级全局状态**（`uidCounter` 会在这里失败） |
| D4 随机对局一致 | 用现有 fuzz 台生成 N 局随机操作（覆盖三代全部协议），每局跑 D1~D3 | 全卡池的隐性随机 |

D4 的规模：至少 200 局随机对局，覆盖三代全部协议注册表。

**D3 是这套测试台的核心价值**：它在你联机之前就能抓出引擎里的隐性全局状态。也就是说 G0 的收益**单机立刻可见**，不必等联机。

## §3 档案格式 MatchFile（G0 / G3）

### 3.1 Schema

```ts
export interface ActionRecord {
  seq: number;          // 单调递增，从 0 开始
  player: PlayerId;     // 执行者座位
  kind: ActionKind;     // 现有 8 种之一
  args?: unknown;       // 随 kind 收窄
  /** 档案层元数据，**不进引擎状态**（§14.2）：
   *  user = 玩家操作；timeout = 决策窗口超时自动合成；ai = 本地 AI 产生 */
  via?: 'user' | 'timeout' | 'ai';
}

export interface MatchFile {
  format: 'compile-match';
  version: 1;                 // 档案格式版本
  cardDataHash: string;       // 卡牌数据指纹（§3.4）
  seed: string;
  setup: {
    draftMode: 'normal' | 'ban';
    draftStarter: PlayerId;
    firstToPlay: PlayerId;
    draftPool: string[];      // defId 列表
    clock?: {                 // 回合计时配置（§14.5）；缺省 = 不启用计时
      decisionSec: number;
      draftSec: number;
      maxSkips: number;       // 免罚跳过额度，默认 2（§14.3）
    };
  };
  players: [{ nick: string }, { nick: string }];
  actions: ActionRecord[];
  result?: { winner: PlayerId | null; reason: string };
  createdAt: string;          // 仅展示用，**不进指纹**
}
```

### 3.2 一份数据，五处复用

| 用途 | 用法 |
|---|---|
| **存档文件**（用户模式的 L2 档案） | 直接存 `MatchFile` |
| **录像 / 复盘** | 同上，加载后用 `ReplayDriver` 逐步重放 |
| **断线重连凭据** | 主机把内存里的 `MatchFile` 发给重连的对手（§5.5） |
| **联机传输内容** | 联机时传的不是 `MatchFile` 而是逐条 `ActionRecord`；但重连时传整个文件 |
| **观战中途加入** | 房主把 `MatchFile` 发给观战者，快速重放到当前局面（§15.2） |

这是本设计里最省力的一处复用：**写一次格式，五个功能同时落地**。

### 3.3 版本迁移

- `version` 单调递增。加载时若 `version < 当前`，走迁移链 `migrate_1_to_2`、`migrate_2_to_3`…，逐级升。
- 若 `version > 当前`（用户装了旧版打开新档案）→ 明确报错，提示"档案来自更新版本的游戏"，**不尝试猜测**。
- `cardDataHash` 不匹配 → 警告并允许"仍要打开"（卡牌数据改动过，效果可能不同），但**联机时直接拒绝**（§5.2）。

### 3.4 卡牌数据指纹

- 对 `src/data/cards.ts` / `cards2.ts` / `cards3.ts` 的卡牌定义（defId / value / 命令文本）计算稳定哈希，作为 `cardDataHash`。
- 用途：防止两台设备卡牌数据版本不同导致规则分歧 ——**这是联机最容易被忽略、后果最严重的一类 bug**。
- 构建时生成的常量，不进运行时状态。

### 3.5 两层本地存储

用户需求里其实有**两套存储**，必须分开设计：

| 层 | 内容 | 载体 | 授权 |
|---|---|---|---|
| **L1 轻量配置** | 昵称、游戏设置、卡组 | 浏览器本机存储（IndexedDB 优先，localStorage 兜底） | 首次进入的授权弹窗 |
| **L2 完整档案** | 账号、战绩、录像、`MatchFile` | 用户自己选择的**本地文件**（可移植） | 用户在保存/导入时显式选择文件 |

**为什么必须分开**：L1 是"轻量、随时可丢"的偏好；L2 是"可移植、换设备靠拷贝"的资产。把整个档案塞进 L1 会撑爆浏览器配额；把设置放进 L2 会导致"我明明授权保存了，换个浏览器设置就没了"。

### 3.6 授权弹窗与游客模式

- **首次进入弹窗**：询问是否允许在本机保存昵称、设置、卡组（L1）。
  - 允许 → 用户模式：L1 可写；进入游戏时可选导入 L2 档案文件。
  - 拒绝 → 游客模式：**L1 与 L2 都不写**，全内存。
- **游客模式**：关闭或刷新即全丢（这是现有行为，无需额外实现）。
  - 对局中 `beforeunload` 给出离开确认（仅为防误操作，不保存任何数据）。
- 授权状态本身需要记录 → **它只能存在 L1**。因此"拒绝"这一选择要么每次进入都问，要么用一个不落盘的会话内标记。设计选择：**拒绝后本次会话内不再询问，下次进入重新问**（真正做到零写入）。
- 用户随时可在设置里改授权（改回拒绝时，提供"清除本机数据"按钮）。

### 3.7 文件读写

| 能力 | Chrome / Edge | Safari / Firefox |
|---|---|---|
| 导入档案 | `showOpenFilePicker` | `<input type="file">` |
| 静默写回同一文件 | ✅ 持久句柄（句柄存 IndexedDB，需同一授权） | ❌ 只能手动"导出下载" |
| 加密档案 | 主密码 + WebCrypto（AES-GCM + PBKDF2） | 同 |

**说明**：Safari/Firefox 下"自动保存"降级为"手动导出"，不影响联机游玩，只影响存档顺滑度。

### 3.8 G3 验收标准

- [ ] 首次进入出现授权弹窗；拒绝后刷新，L1/L2 均为空（可用浏览器存储面板核对）
- [ ] 允许后可保存昵称/设置/卡组，刷新后仍在
- [ ] 导入一份 `MatchFile` 能完整复现对局（配合 `ReplayDriver`）
- [ ] 档案版本迁移测试：手工构造 v1 档案，加载后正确升级
- [ ] `cardDataHash` 不匹配时给出明确警告
- [ ] PWA 可安装、断网可打开（见 §8.1）

## §4 会话层 MatchDriver（G4）

### 4.1 接口

```ts
export interface MatchDriver {
  readonly seat: PlayerId;              // 我是谁
  readonly mode: 'local' | 'replay' | 'ai' | 'net';

  /** 我能操作吗（UI 用它决定是否可点时/是否显示"等待对手"） */
  canAct(kind: ActionKind): boolean;

  /** 提交一个操作（UI 唯一入口） */
  submit(action: Omit<ActionRecord, 'seq'>): void;

  /** 状态变化订阅（驱动渲染） */
  onState(cb: (s: GameState, ctx: { source: 'local' | 'remote' | 'replay' }) => void): void;

  /** 对手在线状态（net 专用，其它返回常量） */
  peerStatus(): { online: boolean; since?: number };

  dispose(): void;
}
```

### 4.2 四个实现

| 实现 | 行为 | 阶段 |
|---|---|---|
| `LocalDriver` | 现行为：本地直接执行，热座两人共用一台设备 | G4 |
| `ReplayDriver` | 按 `MatchFile.actions` 逐步执行，支持暂停/单步/快进 | G4 |
| `AiDriver` | 本地 AI 产生操作（§7） | G7 |
| `NetDriver` | 本地操作发往对端；对端操作驱动本地执行 | G5 |

### 4.3 收口点

**唯一入口是 `main.ts:144` 的 `onAction(a)`。** 现状 `executeAction` 出现在：

- `main.ts:160/181/206/215/217/219/221` —— 均在 `onAction` 内 ✅
- **`main.ts:63`** —— 旁路直呼（协议重排模态的提交）⚠️ 必须一并收口

收口后 `main.ts` 只依赖 `driver`，不再直接 `import { executeAction }`。这样：

- 热座行为不变（`LocalDriver` 就是原来的直呼）
- 换成联机只是换 driver 实例
- **不需要改 `core` 一行**

### 4.4 动作序列化门（settling gate）

**这是 UI 层最大的风险点，做错就是"两边画面错位"。**

问题：现有特效在 `executeAction` 期间**同步**产生，且此时 DOM 是陈旧的（渲染尚未发生）。若远端操作在本地特效仍在播放时到达并立即执行，会出现两个状态转移的特效**交叠**，视觉上错位甚至丢帧。

设计：

- 新增 `src/app/settling.ts`：
  - `markBusy(token)` / `markIdle(token)` —— 由特效层在批次开始/结束时调用
  - 复用现有 `queueStaggered(key, sortKey, run, { windowMs, gapMs, onAllDone })` 的 `onAllDone` 回调作为批次结束信号
  - 远端操作到达 → 入队 `pendingRemote`；`onAllDone`（或静默 `gapMs` 后）→ `drain()`
- **不做乐观执行**：不做"先本地播、稍后回滚"。锁步下双方操作严格有序，序列化就够。
- 超时兜底：若 `onAllDone` 因异常未触发，`windowMs` 上限后强制 drain，避免永久卡住。
- 队列积压提示：积压超过阈值（如 3 条）时 UI 显示"正在同步对手操作"。

### 4.5 G4 验收标准

- [ ] `main.ts` 不再直接调用 `executeAction`（源码守卫测试）
- [ ] 热座全流程与改造前逐帧一致（人工视觉验收 + 现有测试全绿）
- [ ] `ReplayDriver` 能把一份 `MatchFile` 完整复盘，含全部特效
- [ ] 远端操作在本地特效播放中被正确排队，不出现两个特效交叠

## §5 传输层 src/net（G5）

### 5.1 信令与房间码

- 房间码：**6 位 Crockford Base32**（剔除易混字符 I/L/O/U），如 `K7M2QX`。
- 信令频道名：`compile-v1/<房间码>`。
- **无服务器 ⇒ 房间码不入库**：它只是一个"约定的频道名"。房主先进频道等待；加入方进同一频道；双方在频道内交换 SDP/ICE 后**立即脱离信令**。
- 房主不在频道内 → 加入方超时（建议 8s）后提示"房间不存在或房主已离开"。
- 两人撞码概率极低，但仍需兜底：频道内已有对局时，房主回 `busy`。
- **不做房间列表 / 大厅**（裁决 #6）。

### 5.2 握手

```ts
type HelloMsg = {
  t: 'hello';
  role: 'player' | 'spectator'; // 观战者走同一握手，仅角色不同（§15）
  sessionId: string;      // 本局唯一 id，重连时用它找回
  protoVersion: number;   // 消息协议版本
  cardDataHash: string;   // 卡牌数据指纹（§3.4）
  seat: PlayerId;
  nick: string;           // 昵称仅在此处交换，端到端加密
  resuming?: boolean;
};
```

校验顺序（任一失败即拒绝并给出可读原因）：

1. `protoVersion` 不符 → "游戏版本不一致，请双方都更新到最新版"
2. `cardDataHash` 不符 → "卡牌数据版本不一致，无法联机"
3. 玩家位已满 → `busy`
4. 观战位已满 → `busy`（§15.1）

### 5.3 种子承诺（commit-reveal）

开局前：

1. 房主生成 `seed` 与 `salt`
2. 房主发 `commit { hash: sha256(seed + salt) }`
3. 加入方回 `commit-ack`
4. 房主发 `reveal-seed { seed }`（此时加入方只能验 `seed`，还不能验 `hash`）
5. 结束后房主发 `reveal-salt { salt }` → 加入方可验 `sha256(seed+salt) == commit`

**目的**：保证洗牌顺序在开局前已被锁定，房主无法在看到对手的选择后更换洗牌结果。成本几乎为零，且不需要任何服务器。

> **⚠️ 掷硬币的额外约束（G0 Task 6 评审发现，必须在 G5 落实）**：硬币结果现在是 `deriveInt(seed, 'coin', 2)`，即**种子的纯函数**。因此在联机流程里**绝不能让加入方在选定正/反之前拿到 seed** —— 否则它可以先算出结果、再挑必胜的那一面。
>
> 合规顺序（推荐）：加入方先提交正/反的承诺 `commit-face { hash(face + faceNonce) }` → 房主再 `reveal-seed` → 结束后加入方 `reveal-face { face, faceNonce }` 供校验。即**正/反的选择必须先于种子公开**。
>
> 不推荐"硬币用独立 salt 派生"（`deriveInt(seed + salt, ...)` 且在结束时才公开 salt）：那样开局前双方都不知道先后手，而先后手决定草稿顺序，流程无法继续。

### 5.4 通道划分

| 通道 | 类型 | 用途 |
|---|---|---|
| `act` | reliable + ordered | 操作记录、握手、重连、档案传输 |
| `beat` | unreliable + unordered | 心跳、在线状态、表情 |

### 5.5 断线重连（5 分钟窗口）

| 场景 | 行为 |
|---|---|
| 从机断网，页面还在 | 主机保留对局，`peerStatus().online = false`；UI 显示"对手已断线，等待重连…"；主机侧**不推进回合**，且**回合钟同时暂停**（§14.4） |
| 从机 5 分钟内回来 | 从机用同一房间码 + `hello{ sessionId, resuming: true }` 重新握手 → 主机发 `resync-res { MatchFile }` → 从机 `ReplayDriver` 式重放 → 继续 |
| 从机超时未归（>5 分钟） | 主机可手动选择"结束对局"或继续等待（默认继续等待，给玩家决定权） |
| 主机断网 | 同上，方向相反；**主机是状态的持有者**（内存里有 `MatchFile`） |
| 主机关闭页面 | **对局结束**。没有第三方保存对局（红线 1 的直接后果） |
| 任一方刷新页面 | 游客模式下**对局丢失**；用户模式下若已保存可恢复 |

**"断线 ≠ 刷新"必须写进玩家可见的提示文案。**

重连窗口的实现：主机持有时钟参考的 `lastSeenAt`；窗口长度可配置，默认 300s。

**与回合计时的关系（§14.4）**：断线期间回合钟**暂停**，剩余时间冻结；重连后从冻结处继续，不会出现"回来就超时"。断线宽限与回合计时是**两套独立计时**。

### 5.6 移动端专项

| 问题 | 处理 |
|---|---|
| 切后台被系统冻结 JS → 心跳停 → 必掉线 | `visibilitychange` 隐藏时主动发 `bye{paused}`；回到前台立即触发重连流程（§5.5） |
| WiFi ↔ 4G 切换 → 连接失效 | 监听 `iceconnectionstatechange`，`disconnected`/`failed` 时 `restartIce()`，失败则走重连 |
| 触摸交互 | 现有 UI 依赖 hover 与拖拽（`.hand .card:hover`、`bindShieldDrag`），需触摸适配（§6.5） |
| 屏幕宽度 | 现有 `.lane-row` 最小宽 1320px（`styles.css:57`），复用 `ui/zoom-layout.ts` 缩放 |

### 5.7 降级路径：邀请码

当信令不可达或直连失败时：

- 房主侧生成一段**邀请码**（压缩后的 SDP + ICE + 种子承诺）
- 通过任意渠道（微信/Discord/短信）发给对手
- 对手粘贴 → 直接建立连接

做到"只要能上网就能玩，只是多一步粘贴"。**这是 §5 的可达性兜底，不是可选功能。**

### 5.8 TURN 可配置接口

- `iceServers` 从设置读取，默认仅公共 STUN。
- 预留 TURN 配置项（URL / 用户名 / 凭据），**不内置任何中继**。
- 跨境（国内 ↔ 海外）直连质量差时，UI 给出延迟/丢包提示，并提示"可配置中继以改善"。
- 配置中继后需在隐私说明中写明：中继转发**端到端加密**后的数据包，看不到内容，也不存储。

### 5.9 隐私边界（必须对玩家如实说明）

| 组件 | 能看到什么 | 看不到什么 |
|---|---|---|
| 信令服务 | 房间码、IP 地址（技术必然）、连接时刻 | 昵称、卡组、操作内容、对局数据 |
| TURN 中继（若启用） | 加密流量与 IP | 由于 DTLS 端到端加密，**内容不可读**；不存储 |
| 对端玩家 | 你的 IP（P2P 直连的必然结果） | 你的卡组文件、L1 配置 |

> **已知项**：昵称在 §5.2 中经 DataChannel 交换（端到端加密），不走信令明文。

- [ ] 两台设备（PC ↔ 手机）用房间码成功开局并打完一整局
- [ ] 卡牌数据版本不一致时拒绝联机并给出可读提示

## §6 远程对战页面（G2）

### 6.1 布局规格（甲读法）

├────────────────────────────────────────────────┤

对照热座页的差异：

| 维度 | 热座页 | 远程页 |
|---|---|---|
| 战场分割 | 左右（P0 左 / P1 右） | **上下**（自己下 / 对手上） |

| 信息 | 双方全公开 | 自己手牌私密，其余全公开 |

### 6.2 座位相对渲染

- DOM 保留**绝对** `data-player="0|1"`（特效层依赖它定位），但**位置由"我是谁"决定**。
- 新增布局修饰类（如 `.seat-self` / `.seat-foe`）承担位置，渲染时按 `driver.seat` 映射。
- **热座页不改**：两套页面共存，`LocalDriver` 用热座页，`NetDriver` 用远程页。
- **零联机可预览**：加一个"单视角模式"开关，让热座页也能只渲染一个座位 —— 这样 G2 完成后你能立刻在 5173 上看到并验收，不必等 G5。

### 6.3 FX DOM 契约（G1，**必须先做**）

**风险**：`src/ui` 有 26.6k 行特效代码，大量通过 `document.querySelector` 定位元素。新布局若改了 DOM 结构，可能**静默打断几十处特效** —— 正是本项目历史上出过的"整条点名特效从不播"那一类 bug。

G1 交付物：

1. 盘点以下模块依赖的全部选择器与数据属性：
   `ui/effects/index.ts`、`fx-gen2.ts`、`fx-gen3.ts`、`fx-gen3-swap.ts`、`gen3-control.ts`、`compiled-gen3.ts`、`fx-follow.ts`、`zoom-layout.ts`、`fx/delete-shatter.ts`、`fx/discard-cut.ts`、`fx-tornado.ts`

## §7 单人 AI（G9，后续阶段）

- `AiDriver` 与其它 driver 同构：它产生 `ActionRecord`，走同一条 `executeAction` 通道。
- **只在本地运行**，不联网。
- 确定性红利：同种子下 AI 表现可复现 → 调试与回归测试可用固定种子。
- **YAGNI 边界**：本阶段只做"能打完一局、不犯规则错误、有基本线值判断"的启发式 AI。不做搜索树、不做学习、不做难度分级（除非后续明确要求）。
- AI 需要读状态并评估候选操作 → 需要一个 `getLegalActions(s, player)` 式的枚举接口。**注**：`main.ts:234` 的注释提到 `getLegalActions` 不产生 `effect-choice`，说明已有类似设施，G7 先复用它。

## §8 多端打包与更新（G8）

### 8.2 Tauri（PC）

| 平台 | 要点 |
|---|---|
| Windows | 需 WebView2（Win11 自带，Win10 需引导安装）；建议出 `.msi` |
| macOS | **不签名 + 公证会"无法打开"** → 需 Apple 开发者账号（$99/年） |
| Linux | AppImage / deb / rpm |
| 构建 | **三平台分别在对应系统构建**（或用官方 GitHub Actions 模板交叉构建） |

### 8.3 Capacitor（移动端）

| 平台 | 要点 |
|---|---|
| Android APK | 自己签名即可分发；可自行实现应用内更新 |
| iOS IPA | **必须有 Apple 开发者账号 + macOS + Xcode**；分发走 TestFlight / App Store |
| 共用 | 都是 WebView → UI 代码复用；**触摸适配与缩放是真实工作量**（§6.5） |

### 8.4 更新机制（分平台，差异很大）

| 端 | 能否一键更新 | 方案 |
|---|---|---|
| 网页 / PWA | ✅ | service worker `updatefound` → 提示 → `skipWaiting` + reload |
| Tauri PC | ✅ | 官方 updater 插件；程序文件托管在 **GitHub Releases + 国内镜像**（裁决 #9） |
| Android APK | ✅ | 检测新版本 → 下载 APK → 拉起安装（需"未知来源"权限） |
| **iOS IPA** | ❌ **不能自更新** | 平台限制：必须走 App Store 更新。第三方热更新属灰色地带且需额外服务 |

- 版本检测元数据（版本号 + 下载地址 + 校验和）放一个**静态 JSON**，不放任何用户数据。
- **版本一致性**：所有端的 `protoVersion` 必须与联机握手一致（§5.2），否则会各自更新到不同版本后无法联机。

### 8.5 国内外可达性

| 环节 | 海外 | 国内 | 处理 |
|---|---|---|---|
| 静态站点 | ✅ | ⚠️ Cloudflare 在国内无节点，慢/不稳 | 需国内 CDN → **要求域名备案**（政策成本） |
| 安装包分发 | ✅ | ⚠️ GitHub Releases 慢/常失败 | 国内镜像（Gitee Releases / 对象存储） |
| 信令 | ✅ | ⚠️ 公共信道可能不稳 | 信令保持无状态，可多区域部署 |
| 对局数据 | ✅ | ✅ | **P2P 直连，不经过任何服务器** |
| 跨境对局 | ⚠️ | ⚠️ | 中国 ↔ 海外 UDP 直连质量常差 → 需 TURN（§5.8），本阶段只留接口 |

> 运营提示：Discord 在国内被屏蔽，海外 Discord 社区与国内玩家是两个割裂的圈子，会影响分发与更新提示的渠道选择。这不是技术问题，但会影响 §8.4 的落地方式。

## §9 错误处理汇总

| 场景 | 表现 | 处理 |
|---|---|---|
| 房间不存在 / 房主已离开 | 加入超时 8s | 明确提示 + 建议核对房间码 |
| 房间已满 | 房主回 `busy` | 提示"房间已有两名玩家" |
| 版本 / 卡牌数据不符 | 握手校验失败 | 拒绝联机 + 可读原因（§5.2） |
| 指纹不一致（开发期） | 测试台失败 | 视为引擎 bug，必须修，不得忽略 |
| 对手断线 | 心跳超时 | 暂停推进 + 重连倒计时；**回合钟同时暂停**（§5.5、§14.4） |
| 主机退出 | 连接关闭 | 提示"房主已离开，对局结束" |
| 存储授权被拒 | 弹窗选择 | 进入游客模式，全部功能可用但刷新即丢 |
| 档案版本过新 | `version > 当前` | 明确报错，不猜测 |
| 档案损坏 | 解析失败 | 报错并保留原文件不动 |
| 信令不可达 | 建房/加入失败 | 自动提供"邀请码"降级（§5.7） |
| 移动端切后台 | 连接冻结 | 回前台自动重连（§5.6） |
| FX 批次异常未回调 | 队列卡住 | `windowMs` 上限强制 drain（§4.4） |
| 决策窗口超时 | 倒计时归零 | 前 `maxSkips` 次合成合法操作自动跳过（标记 `via:'timeout'`），第 `maxSkips+1` 次判负；断线期间钟暂停（§14.3） |
| 玩家投降 | 点击投降 | 合成 `forfeit` 操作（§14.7），与超时判负共用 |
| 观战位已满 | 房主回 `busy` | 明确提示人数上限（§15.1） |
| 观战者中途加入 | 需要当前局面 | 发 `MatchFile` → 快速重放（无动画）→ 转入实时跟随（§15.2） |
| 观战者全部断开 | 连接关闭 | **不影响对局**，房主仅清理连接（§15.4） |

## §10 测试策略

沿用项目既有惯例（**node 环境，无 jsdom**；UI 测试为 `readFileSync` 源码守卫）：

| 层 | 手段 |
|---|---|
| 确定性 | `tests/determinism/` 四条不变式（§2.7），建在现有 `tests/fuzz` 上 |
| 档案格式 | 往返测试（序列化→反序列化→指纹相同）；版本迁移测试（手工构造旧版本） |
| 会话层 | `LocalDriver` 与现有直呼行为等价；`ReplayDriver` 重放后指纹 == 原局指纹 |
| 传输层 | 消息编解码纯函数单测（**不依赖真实网络**）；握手校验各失败分支 |
| 重连 | 用一个内存版"假信令 + 假通道"跑完整重连流程（可脱离浏览器单测） |
| UI | 沿用源码守卫测试（`tests/ui/*.test.ts`）：远程页必须满足 FX DOM 契约 |
| 端到端 | 两台设备人工验收（本项目无浏览器自动化，最终视觉验收由用户完成） |

**关键设计原则**：把 `net` 层的**协议逻辑**与**浏览器 API** 分离 —— 协议逻辑（消息编解码、握手校验、重连状态机）是纯函数/纯状态机，可在 node 下单测；只有 `RTCPeerConnection` 那薄薄一层需要人工验证。

## §14 回合计时（G6）

### 14.1 计时对象是"决策窗口"，不是"回合"

引擎的 `pendingEffects` 应答者可能是**非回合玩家**（`main.ts:215` 用 `prompt.chooser` 覆盖执行者）。所以按"回合"计时会漏掉最能拖时间的地方。统一概念为**决策窗口**：

| 决策窗口 | 触发条件 | 待决策者 |
|---|---|---|
| 草稿选牌 | `phase === 'draft'` | `draftRoundOwner(draftStarter, draftRound)` |
| 回合操作 | `phase === 'turn'` 且 `step` 允许操作 | `s.turnPlayer` |
| 效果应答 | `pendingEffects.length > 0` | 栈顶 prompt 的 chooser |
| 协议重排 | `rearrange-protocols` 模态打开 | 持有控制组件的玩家 |

一个窗口结束（操作被接受 / 应答完成 / 模态关闭）→ 立即开启下一个窗口的计时。

### 14.2 时钟归属与确定性（核心约束）

**时钟绝不进 `GameState`。** 时钟依赖各设备本机时间，一旦进入状态就必然破坏锁步。

- 时钟由**房主单一持有**（`NetDriver` 的 host 侧）。从机不判定，只显示。
- 房主通过 `beat`（unreliable）周期性广播 `clock { windowId, chooser, remainMs }`；丢失不补，收到即校正显示。
- 到点后房主**合成一个合法操作**，作为普通 `ActionRecord` 经 `act` 通道发出 → 两端按正常流程执行 → **结果必然一致**。
- 重放时**完全不看时间**：`via:'timeout'` 的操作就是日志里的普通一条（§3.1）。
- 从机改本机系统时间**不影响判定**（只影响它自己那一帧的显示，下一次广播即被校正）。

### 14.3 超时后果（已裁决：软提示 → 自动跳过若干次 → 再判负）

**每个玩家每局各有 `maxSkips` 次（默认 2）免罚跳过额度**：

| 该玩家超时到第几次 | 后果 |
|---|---|
| 剩余 20s | 软提示：倒计时变红（**不产生任何状态变化**） |
| 第 1 ~ `maxSkips` 次 | **自动跳过**：按当前窗口合成一个合法操作（回合操作 = 自动推进；效果应答 = 取第一个合法项） |
| 第 `maxSkips + 1` 次及以后 | **本局判负**（对手获胜） |

设计要点：

- **额度按玩家各自计算，不共用**；每局不重置。
- 额度计数**存在操作日志里**（统计该玩家的 `via:'timeout'` 条数），**不新增 `GameState` 字段** → 两端必然一致，重连后从 `MatchFile` 自动恢复。
- 软提示不产生任何状态变化，纯粹是 UI。
- 判负通过新增的 `forfeit` 操作表达（§14.7），与"投降"共用同一操作。
- `maxSkips = 0` 即"一次都不能超时"，退化为纯判负方案。
- **2 次免罚额度同时吸收了网络抖动**，避免一次卡顿就直接输掉。

### 14.4 与断线的关系

- **断线期间回合钟暂停**，剩余时间冻结；重连成功后从冻结处继续。
- 断线宽限（默认 300s，§5.5）与回合计时是**两套独立计时**：宽限用完由对手决定"结束对局 / 继续等"，不由回合计时判定。
- 房主自己断线时同理：钟暂停，恢复后继续。

### 14.5 配置

- 默认：回合决策窗口 **90s**、草稿选牌 **60s**、效果应答 **60s**（均可配置）。
- 免罚跳过额度默认 `maxSkips = 2`（§14.3），可配置。
- 房主在开局设置，写入 `MatchFile.setup.clock`（§3.1）→ 复盘可还原。
- `setup.clock` 缺省 = **不启用计时**；`LocalDriver`（热座）默认不启用。

### 14.6 G6 验收标准

- [ ] 房主与从机的倒计时显示一致（以房主广播为准）；从机改系统时间不影响判定
- [ ] 超时产生的操作在 `MatchFile` 中标记 `via:'timeout'`，复盘能还原同一结果
- [ ] 断线期间钟暂停，重连后从剩余时间继续（不出现"回来就超时"）
- [ ] 四类决策窗口都有计时，**含非回合玩家的效果应答**
- [ ] 前 `maxSkips` 次超时自动跳过、第 `maxSkips + 1` 次判负；额度**按玩家各自计算**
- [ ] 重连后免罚额度从 `MatchFile` 正确恢复；`maxSkips = 0` 时首次超时即判负
- [ ] **草稿阶段**超时也能走到判负（见 §14.7 的守卫问题）
- [ ] 热座模式不受影响；`setup.clock` 缺省时行为与改造前一致

### 14.7 引擎改动清单（本设计**唯一**触碰 `src/core` 的地方）

组合方案把 `core` 的改动收敛为**一个操作类型**：

| 文件 | 改动 | 说明 |
|---|---|---|
| `core/game.ts` | 新增操作类型 `'forfeit'` | `executeAction(s, player, 'forfeit', { reason: 'surrender' \| 'timeout' })` → `s.winner = 1 - player`、`s.phase = 'gameover'` |

**必须注意的守卫问题**：`executeAction` 现有第一行守卫是（`game.ts:122`）：

```ts
if (s.phase !== 'turn' || s.winner !== null) throw new Error('game not in turn phase');
```

它会挡住**草稿阶段**（`phase === 'draft'`）的判负。因此 `'forfeit'` 必须在**该守卫之前**处理，允许 `draft` / `setup` / `turn` 三个阶段。这一条如果漏掉，表现是"草稿阶段超时三次什么也不会发生"——很难察觉，所以写进验收标准（§14.6）。

除此之外，`src/core` 的规则、效果、触发、编译逻辑**不做任何改动**。

> **顺带收益**：`forfeit` 同时支撑"**投降**"功能（对战 UI 需要），两处共用同一操作，不需要第二个引擎改动。

## §15 观战（G7）

### 15.1 拓扑与容量

- **星型：房主为枢纽。** 每个观战者与房主建立**独立的 `RTCPeerConnection`**。
- 观战者**只收不发**（唯一上行：心跳与"离开"）。操作流约百字节级，**带宽不是瓶颈**，瓶颈是房主的连接数与握手开销。
- 人数上限：默认 **8 名观战者**（可配置）。达上限回 `busy`（§5.2）。
- 房间容量语义：2 名玩家 + N 名观战者。玩家位已满而观战位未满时，新加入默认按观战处理，并在 UI 明确告知。

### 15.2 加入流程（含中途加入）

1. 观战者用**同一房间码**加入，`hello{ role: 'spectator' }`。
2. 房主接受 → 发 `MatchFile`（含当前已进行的全部操作）。
3. 观战者用 `ReplayDriver` **快速重放**（无动画，瞬间推进到当前状态）→ 转入实时跟随。
4. 之后与玩家同样接收 `act` 通道的操作流，特效照常播放。

**中途加入是 `ReplayDriver` 快速重放的直接复用** —— 这也是 §3.2"一份数据，五处复用"的第五个用途。

### 15.3 观战者看到什么

- **默认上帝视角**：双方手牌、牌库数量、全部链路完全可见（观战的价值所在）。
- 可切换为**跟随某位玩家视角**：即该玩家看不到的东西也看不到（用于"和朋友一起看自己打"）。
- 布局**复用远程对战页**（§6，甲读法）。泛化方式：`viewSeat: PlayerId`（看谁的视角）+ `handVisibility: 'all' | 'viewSeat'`。
  - 这顺带验证了 §6.2 座位相对渲染的泛化能力：把"我是谁"换成"我在看谁"，布局逻辑不变。

### 15.4 观战与其它机制

- 观战者**不参与任何计时**（不产生决策窗口，§14.1）。
- 观战者可断线重连：同样索取 `MatchFile` 快速重放（复用 §5.5）。
- 观战者离开/断线**不影响对局**；房主仅清理连接。
- **信息泄露说明**：上帝视角意味着观战者可以把信息告知对局中的玩家（外部通讯作弊）。按裁决 #2 不防。若将来要防，唯一办法是**延迟观战**（发送滞后的操作流）—— 本稿不做，记录为将来选项。

### 15.5 G7 验收标准

- [ ] 中途加入的观战者能在 1 秒内看到正确的当前局面（快速重放）
- [ ] 上帝视角 / 跟随视角切换正确，跟随视角下看不到该玩家看不到的信息
- [ ] 观战人数达上限时给出明确提示，且不影响进行中的对局
- [ ] 全部观战者断开不影响两名玩家的对局
- [ ] 观战者不触发任何计时
