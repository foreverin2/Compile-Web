# 运行期浏览器真值自查（工具 + 纪律）

> 2026-09-16 新增。工具：`tools/browser-truth-check.mjs`（**零依赖**，纯 Node + 系统 Chrome）
> \+ 探针页 `tools/browser-truth-probe.html`（两者都**进版本库**）。

## 1. 为什么需要它（三个"静态解算看不见、只有浏览器能看见"的缺陷）

| 缺陷 | 形态 | 为什么静态守卫看不见 |
|---|---|---|
| **R10-2** | `styles.css:422` 的 `.stack { --card-h: 175px }` 声明在**元素自己身上** | 自定义属性只在"该元素自己没有声明"时才继承 ⇒ 任何"把旋钮上提到祖先"的改动**永远赢不了它**。而仓库里的守卫解算的是**声明、权重、源序**——那是"谁该赢"，不是"浏览器判谁赢"。 |
| **R12** | 预览工具条把放牌区挤掉 **98px** | 那是 `flex/grid` **真实求解**的结果。DOM 桩没有布局引擎（`getBoundingClientRect` 恒 0）。 |
| **R17** | `.net-hand-area-foe` 与基类**同权重、被源序吃掉** | 同族：级联的最终裁决权在浏览器。 |

当时的结论是"运行期 `getComputedStyle` 真值自查是唯一能抓住这一族的守卫"，但一直没做成工具。
**这个工具就是那句话的落地**（也是它第一次跑就抓到东西的原因，见 §5）。

## 2. 怎么跑

```bash
node tools/browser-truth-check.mjs                    # 三个场景，全部条目（缺省端口 5199、窗口 2200×1400）
node tools/browser-truth-check.mjs --port 5311        # 换端口（端口被占用时**拒绝启动**）
node tools/browser-truth-check.mjs --shots            # 每场景额外截图 → .superpowers/browser-truth/
node tools/browser-truth-check.mjs --json out.json    # 原始结果落盘（供报告引用）
node tools/browser-truth-check.mjs --only battery.    # 只跑 id 以此开头的项
node tools/browser-truth-check.mjs --tol 2            # 覆盖缺省容差（1px）
node tools/browser-truth-check.mjs --win 3000x1400    # 换测量窗口
node tools/browser-truth-check.mjs --baseline         # **对照基线**：撤掉本轮布局改动再量（见下）
node tools/browser-truth-check.mjs --chrome <路径>    # 指定浏览器（也认 CHROME_PATH 环境变量）
```

### `--baseline`：不碰 git 也能量到"改前"

`--baseline` 让探针在**渲染之前**用 CSSOM 把"本轮 R25 改的那两件事"撤掉
（三个窄屏 `@media` 块 + `.protocol-cell` 的兜底 `min-width`），于是**同一个会话、同一把尺子**
下就能得到"改前 / 改后"两组数字 —— 不必 `git stash`（工作区里常有别的会话的改动，动 git 有风险）。
⚠️ 基线模式下**判定结果没有意义**（期望值描述的是修复后的状态），只看数字；
⚠️ 它撤的是"本轮那两条改动"，与真实"上一轮代码"在我核对过的四个宽度上**逐字相同**
（1920 / 1800 / 1500 / 1366 的轨道与协议宽，见 R25 报告 §2）。

* **退出码**：`0` = 全部在容差内；`1` = 有差异/警告（**含在案差异**）；`2` = 环境错误
  （端口被占、找不到浏览器、vite 起不来、收工自证失败）。
* 它会自己起一个**临时 vite**（`node_modules/vite/bin/vite.js`，不经 `npx`）、用**临时
  `--user-data-dir`** 起 headless Chrome，收工杀**整棵进程树**并打印自证
  （"端口未监听 / 无残留 chrome 进程"）。
* ⚠️ **它刻意不执行 `chrome --version` 之类的探测命令**：那会起一个用**用户默认 profile**
  的真 Chrome（R23 已踩过）。它只用 `fs.existsSync()` 判断可执行文件在不在。
* ⚠️ **它不会去占用已有服务**：开工前若端口已被监听就**拒绝启动**并让你换端口
  （实测有用：本轮就撞上了另一个会话占着 5199）。

## 3. 它测什么（每一项都有"期望值 / 实测值 / 差值"）

* **前提**：容器横向溢出量（`scrollWidth − clientWidth`）。**溢出时下面所有绝对测量都在
  "装不下的布局"里做**（实测：窗口 1500px 时热座的协议列被压成 0、协议图宽 0，整块协议不可见）。
* **几何旋钮链**（R10-2 那一族）：`--card-h` 的**声明处** → 它在**消费元素上**的计算值；
  `--card-w` / `--hand-card-h` 与它们的推导式。
* **卡**：场上卡的布局盒（`offsetWidth/Height`）与视觉盒（`getBoundingClientRect`）——
  热座场上卡带 ±90° ⇒ 两者**互换**；手牌卡宽与步距。
* **协议**：holder 的布局盒 vs 样式表声明；协议图的**旋转后视觉足迹**（远程页 ∓90° ⇒ 与 holder 盒互换）。
* **链路**：装满 7 张时 `.stack` 高 ≥ 声明的 `min-height`（7 张跨度预留）。
* **能量槽（R22 语义）**：DOM 下标 = `[链路槽, 能量槽, 协议格]`/镜像；rect **夹在**本侧链路与本侧协议之间；
  宽 == 该侧内容宽。
* **控制轨**：滑块中心 `top%` == `fxTrackEndFor(seat, control).pct`（页面内 import 同一份源码）；
  两端标签的**文本与端语义**（上端 = 对手、下端 = 自己）+ 水平居中 + 各贴一端 10px。
* **R21 三块布局**：左栏右缘 = 放置区左缘 − `--net-board-gap`；右栏左缘 = 放置区右缘 + gap；
  信息组件在手牌区**上方**；放大框在右栏（左缘 == 右栏左缘）。
* **常驻 FX 层**：烟雾罩盒 == 它的 `.stack-slot`；扫描层盒 == `.battery-shell` 且
  `.scan-horiz` ⇔ "外壳宽 > 高"；已编译协议持久层的 `computed transform` ==
  `rotate(∓90deg) scale(holder宽/200)`（矩阵逐项）且与 holder **同心**、视觉盒互换。

### 期望值必须**单源**（三类来源，每项都标在输出的"期望来源"里）

1. `css:<选择器>#<属性>`：从**同源样式表**读到的声明，再用一个探针盒把 `var()`/`calc()`
   **在真实级联环境下求值**（探针盒挂在被测容器子树里 ⇒ 继承同一批变量）。
   改样式表 ⇒ 期望值跟着变，不可能"两处真相"。样式表里同一条声明**出现 2 次**会**响亮失败**
   （"单源取值失败"警告）——那本身就是"多了一个旋钮定义处"的信号。
2. `dom:<选择器>`：从页面自己的元素推导（相邻元素 rect、"视觉盒 = 布局盒交换"、
   `fxTrackEndFor` 的返回值）。
3. `baseline:<出处>`：**记下来的历史基线**，出处写清"文件:行 + 为什么是那个数"。
   只有"当前 CSS 结构下确实没有单源"时才允许用，且必须在报告里标注。
   目前只有两条：热座手牌卡宽 `130`（`styles.css:387`）与热座手牌步距 `102`（`styles.css:879`）。

## 4. 它**不能**证明什么

* **观感**：好看不好看、读起来顺不顺（只能人眼在 5173 上看）。
* **动画中间帧**：`--dump-dom` 下 **rAF 不产帧**（探针把 rAF 换成 `setTimeout` 才能读到"下一帧"的写入），
  且 CSS `transition` 在虚拟时钟下**不推进**（探针把滑块过渡关掉才读到终点位置）。
  ⇒ 过渡/动画的中间帧、缓动、卡顿，本工具**一概不测**。
* **真实交互**：点击 / 拖拽 / 键盘 / IME —— 本工具**从不派发事件**。
* **跨浏览器**：只跑你机器上那一个 Chromium 内核（Chrome 或 Edge）。
* **门禁地位**：它**不进四道门禁**（门禁跑在 node 里、没有浏览器）。它是**第五道：浏览器**。

## 5. 纪律：什么时候该跑它

> **任何动"布局 / 尺寸 / 落点"的轮次，收尾必须跑一次 `node tools/browser-truth-check.mjs`，
> 并把输出（含在案差异）贴进报告。**

具体包括：`--card-h` / `--card-w` 旋钮、`.net-board` / `.board` 的网格与栏位、停靠栏、
协议与能量槽的落点、控制轨、任何 `calc()` / `var()` 表达式、任何 `justify-self` / `order` /
`grid-column` 改动、以及"把某个组件的尺寸交给图片撑"这类改动。

* 输出里的**在案差异**（`✗（在案）`）是"已诊断、已上报、等裁决"的真差异，**仍然让退出码非零**，
  不许为了让工具变绿而把它们洗成期望值。要用基线，只能走 `baseline:` 那条路并写清出处。
* 容差缺省 **1px**（可 `--tol` 覆盖，也可逐项覆盖）。**论证过的容差**才允许放宽：
  当前逐项覆盖只有三处 —— 旋转足迹互换 1.5px、协议图视觉足迹 1.5px、7 张跨度 2px
  （`--card-h` 是"比例基准"而不是"实测卡高"，`render.ts`/`styles-net.css` 的注释写明过）。
* **布局类守卫的四道门禁之外**，这一道是唯一能看见"级联真实胜负 / 真实 grid 求解"的。

## 6. 首跑结果 + 一次**判据自我修正**（2026-09-16，工具第一次真跑）

* 条目：**通过 80 / 新差异 0 / 在案差异 2 / 警告 0**（窗口 2200×1400；热座 + 远程页两个席位）。
* ⚠️⚠️ **首跑时我把两条 `layout.overflow.*`（`.lane-row` 119px / `.board` 166px）读成了
  "栅格装不下"，并据此写进了"在案差异" —— 那个**诊断是错的**。**同一轮里工具的"溢出定位"
  输出自己把它推翻了**：越界最多的后代全是 `position: absolute` 的
  `battery.battery-stable(+119px)` 与 `battery-overflow(+165.8px)`，而 `.lane-row` 的四条轨道
  实测 `660 177 177 660`（合计 1704 = 内容宽 1704）——**栅格本来装得下**，
  那 119px 是 `.battery { left/right: -120px }` 的**设计外挂**（能量槽挂在链路框外侧）。
  ⇒ 处置：**判据拆成两条各管一件事** —— `layout.gridFit.*`（静态轨道装得下，才是真判据）+
  `page.hScroll`（用户可见的横向滚动条）；原来那两条 `scrollWidth` 项改成**只报数不判定**
  （`noteOnly`），因为"容器 scrollWidth 大于 clientWidth"对绝对定位装饰**本来就不成立**。
* 顺带被这套探针**证伪**的另外两次"疑似缺陷"（都是探针自己的假象，由自检抓出）：
  协议 defId 用了 `fire-0`（协议图路径其实按**协议族名** `fire/` 拼 ⇒ 6 张图 404、协议盒塌成 20px）、
  以及"左右栏贴边"的期望没把 `--net-board-gap: 2px` 算进去（那不是缺陷，是列间距）。
* **一次真实的用户可见条件（已上报、未修）**：`page.hScroll` = **66px**（六档宽度都一样）——
  `.battery` 的外挂（叠加点数 >10 时的 `.battery-overflow`）超出了 `#app` 的 100px 内边距。
  修它要动电池外挂量或给 `#app` 加 `overflow-x: clip`，**两者都会改用户已验收的观感** ⇒ 留给裁决。

## 7. R25 · 窄屏降级（这条纪律的第一次实战：`styles.css` 的**放行**）

### 7.1 为什么放行 `styles.css`（它是热座页的红线文件）

用户点名的修复（"给协议列一个最小宽 + 允许链路列收缩 + 窄屏缩一档"，三选一里的 A）
**只能**落在热座页样式表里。所以本轮**只允许**改与本修复相关的三处，其余尺寸一律不动：

| 改动 | 位置 | 对应哪条要求 |
|---|---|---|
| `.protocol-cell { … min-width: 80px }`（**无条件兜底**） | `.protocol-cell` 规则 | 要求 2"协议永不允许塌成 0 宽" |
| `@media (max-width: 1709px)`：`.lane-row` 链路列换 `minmax(0,1fr)` + `.protocol-cell { min-width: 210px }` + `.stack { --card-h: 117px }` | 新增 | 要求 3"窄屏优雅降级"（媒体查询里才允许链路列收缩）+ 要求 2 的"完整 200px"那一层 |
| `@media (max-width: 1610px)` / `(max-width: 1467px)`：只重声明 `.stack { --card-h }` | 新增 | 要求 3"按同一个旋钮缩一档"（两档 + 一档 = 三级阶梯） |

**没动**：`#app { max-width: 2000px; padding: 0 100px }`（那是用户没选的方案 B）、
`.lane-row` 的**无条件** `minmax(660px, 1fr) auto auto minmax(660px, 1fr)`、`.protocol-img { width: 200px }`、
`.stack { --card-h: 175px }`、手牌卡宽 `130px`、以及任何别的尺寸。

### 7.2 断点是怎么定出来的（实测 + 反解）

`.lane-row` 的内容需求 = 2 × 链路列 + 2 × 协议列 + 3 × 10px gap；协议列进档后 = **210px**；
链路列 = 7 张卡的**视觉跨度**（卡 ±90° 横躺，量"最后一张右缘 − 第一张左缘"）+ 槽的 padding/border **35px**，
`--card-h: 175` 时实测 **660.1 + 35 = 695.1**；`#app` ⇒ 内容宽 = min(视口, 2000) − 200。

* **第一档断点由"兜底最小宽"反解**：兜底 80px 一旦生效就不能让栅格溢出 ⇒
  内容宽 ≥ 2×660 + 2×80 + 3×10 = **1510** ⇒ 视口 ≥ **1710** ⇒ 断点取 **1709**
  （⇒ 视口 ≥ 1710 时**一个媒体查询都不生效**：用户验收过的宽度逐字不变）。
* **每档的 `--card-h` 由"该档覆盖范围的**最窄处**装得下"反解**（不是最宽处！第一版按最宽处取 131，
  到区间尾部又差 49px/侧）：`2 × (跨度(h) + 35) + 450 ≤ 该处内容宽`，跨度(h) ≈ `3.7721·h + 0.4`
  （四点实测拟合：175→660.1 / 150→565.8 / 118→445.1 / 100→377.2，误差 ≤0.5px）。

| 档 | 断点（视口） | `--card-h` | 7 张跨度(+槽) | 该档最窄处余量 |
|---|---|---|---|---|
| 满档 | ≥ 1710（不生效） | 175px | 695.1px | ——（保持现状） |
| 一档 | ≤ 1709 | 117px | 476.4px | +7.5px @1611 |
| 二档 | ≤ 1610 | 98px | 404.7px | +7.9px @1468 |
| 三档 | ≤ 1467 | 83px | 348.1px | +1.0px @1348 |

### 7.3 "设计宽不变"是一条**硬要求**（用户："我对现在这个页面的布局很满意"）

它被两条腿同时钉住（一条声明、一条浏览器）：
* **声明腿**（进四道门禁）：`tests/ui/hotseat-narrow-fallback.test.ts` 的 R25-4 ——
  无条件列模板 / `--card-h: 175px` / `.protocol-img{width:200px}` **逐字未变**，
  且 `styles.css` 里**没有任何媒体查询的断点 ≥ 设计宽视口 2000**；
* **浏览器腿**（本工具）：设计宽口径（视口 2000 / 内容 1800）下，
  修复前后**逐项实测值 82/82 完全相同**；1920 与 1800 两档的轨道/协议宽/卡片尺寸也**逐字相同**
  （见 R25 报告 §2 的六档矩阵）。

### 7.4 纪律补一条

> 动**布局 / 尺寸**的轮次，光跑一次单宽度不够 —— **至少跑六档宽度矩阵**
> （`--win 1920 / 1800 / 1700 / 1610 / 1500 / 1366`），并对"用户当前在用的那一档"
> 用 `--baseline` 做**前/后对照**（证明"没改观感"）。
