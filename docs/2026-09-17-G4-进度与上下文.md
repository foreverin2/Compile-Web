## 3. 已知缺口清单（**逐条给事实 + 代价**）

> 每一条都指向真实文件与行号。**"代价"写的是"如果不管它会怎样"**，不是复述标题。
> 这些是本波各轮评审如实登记的，原先散在计划 §5 各任务的「已落地」块里，**这里逐条收进来**。

**① devmode 旁路未 `note()`（`main.ts` 里 `note(` 零命中）。**
事实：`DevModeHost`（`src/ui/devmode.ts:30-31`）**没有旁路回调**，三个旁路（`devmode.ts:328-341`/`356-373`/`393-408`）直接改 `state` ⇒ `main.ts` 无从知道发生了注入、`note()` 无从调用；`main.ts`（去注释）里 `note(` **零命中**（唯一出现是注释）—— 该现状由 T7 的新腿 `tests/ui/g4-closure-guard.test.ts` 的 **L3** 钉住（将来补上 `onBypass` 时它会立刻变红，逼着同时改本文档）。
代价：注入过的对局**不可忠实重放**，且档案里**不会留下"发生过旁路"的痕迹** —— 而 `MatchFileRecorder.note()` 的设计用意恰恰是"否则'档案为什么复现不出来'会变成无法调试的问题"（`match-file.ts:507-513`）。**不是新引入的不实陈述**：`devmode.ts:323` 已有承重注释"注入过的对局不可重放"。
**最小未来修法**：给 `DevModeHost` 加可选 `onBypass`，`main.ts` 转 `driver.note`。（T4 当时不做的原因：要动 `src/ui/devmode.ts` + `main.ts` 的 `initDevMode(...)` 调用区，而那个调用区被 `tests/ui/net-preview-wiring.test.ts:249-254` 的 **400 字符窗口**约束着，且 `main.ts` 当时被 T4/T5 两个任务同时占用。）

**② 看门狗 `diagnostic` 不上屏。**
事实：驱动的看门狗诊断走 `cursor().diagnostic`（`src/app/match-driver.ts`），而控制条的状态形状 `ReplayBarState`（`src/ui/replay-bar.ts:50-56`）只有 `error` 槽、**没有 `diagnostic` 槽**；`main.ts:328` 的装配只传 `error: c.error ?? replayHostError`。
代价：看门狗触发时（= 宿主漏了一次 `settle()` 的兜底路径）**玩家看不到那条诊断** —— 屏上只表现为"这一步停了很久"。按裁决**不把它塞进 `error`**（两者语义不同：`error` 是引擎抛错，`diagnostic` 是"宿主该回话没回话"），因此这是一个**有意保留的可见性缺口**。

## 4. 方法学教训（**11 条，逐条保留原证据与"哪次变异/哪条命令"**）

> 这些是计划文档 §5「★ 方法学教训（G4，T7 必须全部收进收口文档的教训清单）」的**逐条搬运**，**不抽象化**：每条都保留当时的具体证据。顺序按计划原文（第 11 条在原文档里就是插在第 4 与第 5 条之间的）。

### 第 1 条：「不能区分世界」的探针不是判别器，只能配对使用。

T3 用 `probe-f1-oldmodel.mjs` 证明"旧模型对 F1 变异是瞎的"。评审复核后指出：该探针**按设计只读 `styles.css`、从不读被变异的那张表** ⇒ 它在**变异体与纯净体上都 exit 0 并打印同一句"旧判据全绿"**，退出码**不区分世界**。
⇒ **正确用法**是"与 `probe-f1` **配对**成立"（一个证明旧公式的数据来源只有一张表，一个证明新公式双向可辨），**不能**单独写成"复现了缺陷"。
⇒ **通用规则**：任何探针在被当作"缺陷证据"之前，必须先在**纯净树**上跑一次，并**确认它报的是"缺陷不存在"**；若它与世界无关（恒绿/恒红），它就只能作为**差分对照的一半**。
⇒ 这与本仓已有的"`if (false)` 包裹也能骗过锚点唯一性 + 摘要变化"是**同一族**教训（机制满足了、语义没满足），**这是该族的第二次出现**。

### 第 2 条：注释里宣称的"实测依据"必须与代码逐字相符 —— 归因错了比没有注释更坏。

T1 的头注（`match-replay.ts:49-55`）与 `match-recorder.test.ts:224-231` 都写着"若只对 compile/refresh 还原…指纹仍不等（**实测 turn 9/10/15**）"。一审的 **M5** 把它证伪了：只留 `rearrange-protocols` 那一半 ⇒ **41 项全绿、0 红**。真相是 `rearrangeProtocolSlots` 不碰 control，所以**只有它**需要助手提前插入归还；compile/refresh 的"归还 log 在动作 log 之前"**引擎自己就保证了**（`game.ts:143/156`）⇒ 那半是空转的，而注释把 `rearrange` 那一半的**实测数字记到了 compile/refresh 头上**。
⇒ **规则**：引用"实测"时**必须能指出是哪条腿、哪个构造、删掉哪一行会红**；写不出这个链条的"实测"一律降级为"推断"。**计划自己也在 §3.1 犯了同一个错**（第一版写"重放不需要额外模拟"），已回填纠正 —— 规划者的注释同样受这条约束。
⇒ **T7 的落地**：这条教训正是 §3 缺口 ⑬（`match-driver.test.ts:610` 的断言消息措辞）的处置依据。

### 第 3 条：探针自身也会带 bug，且它的 bug 方向恰好是"说没缺陷"。

T3 为 F6 扩写 `probe-f5.mjs` 时，第一版报内联上限 **601 而不是 620**（在 F6 变异体上也会说"缺陷没有复现"）。原因：它按"函数体里出现过 `${param}`"反推 helper 的形参位置，而 `layer(cls, z)` 体里还有 `` `${cls} g3fx-layer` `` ⇒ 取到了 `cls`，**620 从未进候选面**。改为从 `z-index:${...}` 那一句直接取形参名后，探针报 `92 条 ⇒ 620`（变异体 20000）。
⇒ **规则**：探针报"没缺陷"时，先怀疑探针 —— 至少要用一个**已知会红的变异体**验证它确实会红（即 `probe-f5 full` 那种双向可辨性）。这是第 1 条的正向用法：**能区分世界**是探针上岗的最低要求。

### 第 4 条：「0 个测试看起来是绿的」这一族有**三个不同**的入口，必须能指到具体命令才叫"实测"。

T1 在上报时写"镜像里 `--reporter=basic` 在 vitest 4 不存在 ⇒ 整轮跑 **0 个测试却可能退 0**"。复验**实测否证了机制**：`npx vitest run --reporter=basic <file>` ⇒ `⎯ Startup Error ⎯ Failed to load custom Reporter from basic` + `ERR_LOAD_URL`，**exit=1**（启动期硬错，不是假绿）；`--help` 的合法列表里确实没有 `basic`（真、但无害）。
⇒ **真正的形态是这三个**（三个都要背下来）：
1. `npx vitest run -t "<不存在的腿名>"` ⇒ `Test Files … skipped` / `Tests … skipped`、**exit=0** —— **千万别用 `-t <中文腿名>` 判绿**（本仓 G3 已栽过一次，这次是**误把账记到 `--reporter` 头上**）。
2. **镜像不被 `include` 收编**（`vite.config.ts:5` 是 `tests/**/*.test.ts`）⇒ 裸 `npx vitest run` 从仓库根跑镜像会**一条都不跑**；必须 `--config <镜像>/vitest.config.ts` 或 `--root <镜像>`。
3. **临时脚手架放进 `tests/`**（G4 实测：T6 的 `tests/t6-derive-tmp.test.ts` 被自动收编，文件数 144→**145**）⇒ 它不仅会被跑，还会**污染所有人的门禁读数**。
⇒ **规则**：任何"全绿"结论都必须附带**该次运行的 `N files / M tests`**，且 `M > 0`；报告里出现"我用 `-t` 只跑了那一条腿"或"我排除了某些文件"时，**必须写明排除面与理由**。
⇒ 这也是第 2 条（归因）的姊妹条：**教训也必须能指到可复现的命令与输出**，否则它只是"听起来像教训"。

#### 第 4 条的补记：`--config` 不换 root（T5 实测，比前三种更隐蔽）；附全波镜像审计结论。

T5 实测（vitest 4.1.11）：从**仓库根**跑 `npx vitest run --config .superpowers/g4t5/pre/vitest.config.ts tests/ui/local-data-screen.test.ts` ⇒ 输出头是 `RUN v4.1.11 E:/…/compile`（**仓库根**）、跑的是**共享工作树**的源码与测试 ⇒ **M0 变异体上仍报 `1 passed / 32 passed`、exit=0（假绿）**。改成 `--root .superpowers/g4t5/pre` ⇒ 输出头变成 `RUN … E:/…/.superpowers/g4t5/pre`，同一变异体上 `1 failed | 31 passed`、exit=1。
⇒ **第 4 种形态（最隐蔽的一种）**：不是"一条都不跑"，而是"**跑了另一棵树**"—— 变异打在镜像上、测试跑在工作树上，于是**变异看起来毫无效果**（如果预期是"红"，你会得到"绿"，并把结论写成"这条腿没牙"；如果预期是"绿"，你会得到一个假绿）。
⇒ **识别方法（一句话）**：**读输出头的 `RUN vX <root>`** —— 它逐字打印 vitest 解析出来的 root。**root 不是镜像 ⇒ 这次运行与你的变异无关。**
⇒ **全波审计（规划者 2026-09-17 实查）**：本波四个跑手**都**把 root 落在了镜像上 ⇒ **已验证的变异证据不受影响**：T2 的 `mutate.mjs:81-82` 与 `probe-reports.mjs:37-38` 用 `{ cwd: MIRROR }`；T4 的 `mutate.mjs:66-67` 同样 `{ cwd: MIRROR }`；T1 报告自述"从镜像 cwd 跑"；T3 的镜像 config **显式** `root: fileURLToPath(new URL('.', import.meta.url))`。⇒ **保留结论，但把纪律写死**：镜像跑法**要么** `--root <镜像>`，**要么** `{ cwd: 镜像 }` + `--config vitest.config.ts`（相对路径），并且**必须在报告里抄下输出头的 root**。
⇒ **T7 的落地**：本任务的 harness 用 `{ cwd: MIRROR }` + 相对 `--config`，报告里逐条抄了 `RUN v4.1.11 …\.superpowers\g4t7\mirror`。

### 第 5 条：边界纪律在"临时"两个字上最容易破。

T6 在 `tests/` 下建了一个自述"跑完即删，绝不提交"的脚手架，被 vitest 收编（144→145），于是**另一个子代理的复验报告把 145/1818 当成了"当前树"**记下来。
⇒ **规则**：临时物一律 `.superpowers/<任务>/`（已 gitignore）；`tests/**` 与仓库根都**不是**临时区。**"我跑完会删"不是理由** —— 在你删之前，别人的门禁读数已经被你改过了。
（**本波这条规矩被破了两次**：T6 的 `tests/t6-derive-tmp.test.ts` 与 T2 的 `tests/zz-probe-crit4.test.ts`。第二次是**在第一次已被通报之后**发生的 ⇒ 这条不是"提醒"，是**必须写进每个任务的派工简报**的硬约束。）
⇒ **T7 的落地**：本任务全部临时物在 `.superpowers/g4t7/`（mirror / probes / harness / 报告），**没有**在 `tests/**` 或仓库根放任何临时文件。

### 第 6 条：退出码必须避开管道测量（Windows/PowerShell 实测）。

T1 为了订正第 4 条，第一次用 `npx vitest run --reporter=basic <f> | Select-String …` 量退出码，得到 **exit=0**；重定向到文件再读 `$LASTEXITCODE` 才拿到真值 **exit=1**。
原因：**管道之后 `$LASTEXITCODE` 是管道末端 cmdlet（`Select-String`）的退出码，不是 `npx` 的**。
⇒ **规则**：任何"退出码"证据都必须**不经管道**测量（`cmd > file 2>&1` 再读 `$LASTEXITCODE`，或直接 `; Write-Output "exit=$LASTEXITCODE"` 紧跟命令）。
⇒ 这条与第 4 条是**同一族**：**测量的对象被测量方式掉了包**。它也正是 T1 最初把"`--reporter` 不存在"与"0 测试退 0"两件事混成一件的**直接原因** —— 一个假的 `exit=0` 让它以为那个 reporter 是"静默假绿"。
⇒ **T7 的落地**：变异 harness 用 `execFileSync` 直接拿 `status`（不经任何管道），四道门禁的退出码用 `$LASTEXITCODE` 紧跟命令读取。

### 第 7 条：层叠问题只能**问浏览器谁在最上面**（hit test），不能读 CSS 属性 —— `getComputedStyle` 会对"被忽略的 `z-index`"照样回话。

T6 做 M2 时，规格给的最简形态（**只**写 `shield.style.zIndex = '0'`）实测**全绿**。原因：`.board` 在热座页是 **`position: static`**（`styles.css:20` 只写 `display:flex;flex-direction:column`）⇒ **内联 `z-index` 对非定位元素被浏览器完全忽略**；而 `getComputedStyle(el).zIndex` **照样把设进去的值原样读回来** —— 于是任何"读属性"的判据都会说"压下去了、设上了"，**而浏览器根本不这么算**。修法：注入时同时给 `.board` 加 `position:relative`（只改定位方式、**几何零位移**）⇒ 三条判据全红（`overCenter`/`overCard` true→false、`blocksBoard` 9→3，命中链变成 `div.player-strip → div.board-grid → div.board`）。
⇒ **规则**：凡"谁盖住谁 / 能不能点到"的问题，**判据必须落在 `elementFromPoint`（或 `getBoundingClientRect` 的几何关系）**上，**不许**落在 `getComputedStyle` 读到的 `z-index`/`position` 上。这是"行为腿 > 文本腿"在 CSS 上的那一面：**`getComputedStyle` 读的是"作者写了什么"，`elementFromPoint` 问的是"浏览器算了什么"。**
⇒ **T7 的落地**：§2.2 报的 `replay` 场景判据里，承重的两条正是 `replay.shield.overCenter` / `overCard`（`elementFromPoint`）与 `replay.bar.aboveShield`。

### 第 8 条：取证工具本身会给出**结构性假信号**，第五条门禁的两个实测坑。

1. **`TIME_WAIT` ≠ 正在监听**：裸 `netstat -ano | Select-String ':5199'` 会打出**满屏 `TIME_WAIT`**（历史探测留下的**已关闭客户端 socket**、PID=0）⇒ 看起来像"端口还被占着"，或反过来让人忽略真正的 `LISTENING` 行。**必须**只判 `LISTENING` 行，或直接做连通性测试（`Test-NetConnection 127.0.0.1 -Port 5199`）。
2. **按命令行筛进程会自匹配到"查进程的那条命令自己"**：用"命令行含 `btc-chrome-`"筛残留 Chrome 时，**DSH 自己的 subprocess runner 会被匹配**（`dsh-subprocess-local/.../runner.js -- pwsh -Command "…btc-chrome-…"`）⇒ **恒假红**（永远"有残留"）。**必须**排除 `dsh-subprocess` / `runner.js`。
⇒ **规则**：收工自证这类"证明某物不存在"的检查，**必须先证明它在"确实没有"的世界里会返回空**（即在一次干净的运行上试一次）；否则"查不到"与"查错了"不可区分。这与第 1 条（探针要能区分世界）是**同一条规则**用在"否定性证据"上。

### 第 9 条：修守卫时，"修洞的动作本身"会静默失效 —— 两个已经发生的形态。

T2 为三种绕行形态（`window.setTimeout(`、`globalThis["setTimeout"](`、`(setTimeout)(`）扩写判据 9 的正则，**第一版两处都静默失效**（探针的双向锚点 9 正控 + 6 反控抓出）：
1. **可选前缀 + 后顾断言（lookbehind）组合**：写成 `(?:window|globalThis|…)?` 时，`(?<![\w$.])` 落在**前缀的开头**而不是全局名的开头 ⇒ `globalThis["setTimeout"](` **静默 0 命中**。正确形态是让后顾紧贴真正要判的那个名字（前缀放后顾之后）。
2. **把引号写成字符类 + 把分组前缀当普通字符**：`['"]${NAME}['"]` 里的 `['"]` 被当成**单元素字符类**、而 `(?:` 被当成普通字符 ⇒ **计算属性分支同样静默失效**。
⇒ **规则**：任何"扩面/补洞"的正则改动，**必须先用一条正控样本证明它能命中**（这里的正控是"把三种绕行各写一个合成样本，断言都被抓到"），再谈它是否覆盖了目标。**"我加了这条正则" ≠ "这条正则会命中"** —— 这与第 1/3 条同族：**动作发生了，语义没发生**。
⇒ 附带结论（对 T4）：**不要指望判据 9 替你抓定时器**。它的正则面永远追不上写法空间 ⇒ **`src/app/**` 里一个定时器都不许出现**是**纪律**，不是"有腿兜着"。
⇒ **T7 的落地**：本任务给 `TIMER_CALL` 补泛型/可选链两段时，先写了**形态边界的正控 + 反控**（`g4-closure-guard.test.ts` 的第一条腿），并另加**两份副本一致性腿**；变异 M2 实测两条腿都红。

### 第 10 条：本机（Node v22 + Windows）的 `fs` 递归操作会硬崩 node —— 崩溃是"静默"的。

T4 搭隔离镜像时实测：`fs.cpSync(dir, dst, { recursive: true })` **硬崩 node**，退出码 **`-1073740791` = `0xC0000409`**，且 **stdout/stderr 全空、零错误信息**（本仓更早已观察到同族现象，报的是 `0xC0000419`）。带 **junction** 时 `rmSync(path, { recursive: true })` 同族危险。
⇒ **规则**：镜像构建/清理**不要用** `cpSync(recursive)` / `rmSync(recursive)`；**先 `cmd /c rmdir <junction>` 摘链接再删**，复制改用**逐文件 read+write**（可复用的实现：`.superpowers/g4t4/make-mirror.mjs`、**T7 的 `.superpowers/g4t7/make-mirror.mjs` 同一套**）。
⇒ 这条与第 4/6 条同族但更狠：**它是一个"没有任何输出的失败"** —— 若把它当成"命令没跑"或"跑通了"，后续所有结论都建立在一个没发生的动作上。

### 第 11 条：变异镜像会吃 Vite 的陈旧转换缓存 ⇒ "变异没生效"的假绿（跨变异，而非单次编辑）。

T2 的 J 轮实测：`mirror/node_modules/.vite` 以**路径**为键缓存转译结果，而**镜像路径固定** ⇒ 两次变异之间会复用**上一次的编译产物**。现象：J1 变异注入后**探针仍全绿**（"变异没生效"）；`rmSync(mirror/node_modules/.vite)`（含 `.vite-temp`）之后**同一变异立刻变红**。
⇒ **规则（★ 已按 T4 的安全纠正改写 —— 我第一版写的"删 `mirror/node_modules/.vite`"是危险建议）**：镜像是用 **junction** 把 `node_modules` 指到共享树的 ⇒ **删镜像里的 `node_modules/.vite` 等于删共享缓存**，会打到并行任务与正在发服务的会话。**正确做法：把缓存关进镜像自己的目录**（镜像配置里设 `cacheDir: '.vitest-cache'`，必要时连 `test.cache.dir`），**每次变异运行前删那个目录**。
**T4 的对照实验（本轮读数是否受污染）**：同一条变异（M4b）跑两遍 —— 不删缓存 `1 failed | 145 passed`、删缓存**完全相同**的读数 ⇒ **本轮读数未被陈旧转译产物污染**；此后 7 条变异一律在"删缓存"形态下跑。
**★ 对已有证据的追溯评估（必须如实写进收口文档）**：
- 本波所有**承重**变异报的都是**预期腿上红 + 独立探针自己复现缺陷**（例如 T2 的 `M1 actions=0`、`M2 refusal=undefined ok=true`、T1 的 M4 在预期腿红且探针双向可辨）。**陈旧缓存无法解释这类读数** —— 它只会给出"绿"或"错腿红"，不会给出与缺陷对应的探针输出。
- 更强的证据：T2 在 **J 轮（已按本条修法清缓存）**里**复跑了 M1/M2/M3/M6/M7/M8/H1/H2/H3**，**全部按预期打红、还原后两遍全绿** ⇒ **T2 那批变异证据在修正后的 harness 下被再确认**。
- **仍存的保留**：T1/T3/T4 的镜像 harness 是否清过缓存**未逐一体检** ⇒ 这三者的历史读数**带上"未在清缓存形态下复验"的标注**（= §3 缺口 ⑤）；**任何"某条腿不红"的结论，在清缓存后重跑一遍之前不得采信**（"红"的读数受影响小，"绿"的读数受影响大）。
**附：探针构造的两条纪律（T2 的 J 轮交出）**：① **探针的"世界判定"必须是"只认自己那条标记"**（写成"源码里有任何 `__MUT_`"⇒ 每个变异体上所有探针都走变异分支、互相污染，噪声满屏）；② **"探针构造失败"不得误报成"缺陷复现"** —— T2 的 M5 探针第一版"走到末尾再问 `exhausted`"在**纯净树**上就停在 `pos=3/40`（带 `error` 的世界走不到末尾），它把构造失败当成了复现 ⇒ 已删该探针并把事实写进代码注释。**遇到"探针在纯净树上也不对"，先怀疑探针**（第 1/3 条）。
⇒ **T7 的落地**：镜像配置 `cacheDir: '.vitest-cache'` + 每次变异前 `clearCache()`；**绝不**删 `mirror/node_modules/.vite`；报告里逐条记了 SHA 前→后与还原读数。

### 7.2 正式验收三项

1. **重启一局再导出/导入（跨会话）**：重启浏览器（清掉内存态）→ 导入上一份档案 → 重放 ⇒ 仍然能重演。**这证明档案是自足的重连凭据**（G5 的断线重连全靠这一条）。
2. **两个 profile 的档案往返**：profile A 打若干步 → 导出 → profile B 导入 ⇒ 如果两侧**卡牌数据不同**，必须看到**卡牌数据不一致的警告**，而**不是**静默乱码或崩溃。
3. **长局重放的观感**：找一局 ≥ 30 步的档案重放，看**长时间连续重放**下有没有：动画抖动、控制条消失/叠加、进度与盘面不符、结束时不显示"已重放完"。

### 7.3 已知观感差异（**请不要当 bug 报**）
- **4× 不会快 4 倍**：倍速只缩短**步间隔**，长特效（抽牌 / 揭示 / 编译环）仍占满真实时间（D10）。真正的"瞬时快进"是 G7 观战"快速重放"的独立任务。
- **重放页上 devmode 控制台被遮罩挡住**（`.replay-shield` 的 z-index 12500 高于 devmode 模态的 1200）⇒ 想用 devmode 指令就**在进入重放之前**做。
- **重放页不能"从这一步接着打"**（D3 的代价：重放复用同一条编排 ⇒ `state` 指向重放局）。
- **"最近一局"刷新页面后消失**（D13：档案不落盘）—— 屏上文案已写清"档案要自己导出保存，本机不替你留"。
- **重放到终局只弹一次胜利横幅**（`winOverlayShown` 是闩锁，G4 的重放只前进）。

### 7.4 机器验证覆盖不到的地方（**本轮最需要人眼补位**）

- **看门狗诊断不上屏**（缺口 ②）：它只在"宿主漏了一次 `settle()`"时出现，而那条路机器侧由 8s 看门狗兜 ⇒ **人眼几乎看不到**，但如果你真看到"某一步停了很久又自己动了"，那就是它。
- **注入过的对局不可忠实重放**（缺口 ①）：用 devmode 加过牌 / 改过状态的对局，导出的档案在别处重放会**走到某一步就停**（且**档案里没有留痕**）。这是**已知缺口**，不是新 bug。
- **真应用（`index.html` → `main.ts`）的"导入 → 重放"路径没有机器真值**（缺口 ④/⑪）：第五道门禁的 `replay` 场景走的是**探针入口**（第二份装配）⇒ 那条真装配路径**只有你**能验（= 上面 7.1 的第 3 件）。
