## §2 Global Constraints（每个任务都适用）

1. **`src/core/**` 本阶段零改动。** `forfeit` 的引擎动作属 G6。若某个任务认为非改不可，先停下来改裁决，不要顺手改。
2. **`src/net/**` 是纯层**：不得出现浏览器 API（`window` / `document` / `navigator` / `localStorage` / `indexedDB` / `fetch` / `WebSocket` / `RTCPeerConnection` / `serviceWorker`）、不得出现 `Math.random` / `Date.now` / `performance.now`、不得直呼定时器（`setTimeout` / `setInterval` / `requestAnimationFrame`）、不得 import `src/ui/**`、不得 import `node:*`。**能力一律注入。**
   - 这条不是口号：`tests/app-purity.test.ts:44-118` 是**生成式**递归扫目录的守卫，T1 会把它照搬一份覆盖 `src/net/**`。
3. **浏览器 API 只能出现在 `src/ui/net-browser.ts` 这一个文件里**，形状照 `src/ui/archive-fs-browser.ts:601-607`（它自称是 `FileIoCapabilities` 的"唯一出处"）。纯 → 浏览器之间的**唯一接口**是 `src/net/transport.ts` 里的注入接口。
4. **零运行时依赖**（裁决 #12，`:68`）：WebRTC / WebSocket / WebCrypto 都是浏览器内置，`package.json` 的 `dependencies` 保持为空。**不得 `npm install` 任何东西**（含 puppeteer 之类；CDP 用 Node 自带的 `WebSocket`/`fetch` 手写）。
5. **锁步**：两端都跑引擎，只交换操作指令（裁决 #7，`:37`）。**不许**出现"服务端权威"或"只有主机跑引擎"的方案（红线 2，`:47`）。
6. **文案同源**：任何面向玩家的隐私/信令说明只能来自 `src/app/privacy.ts`，消费方**引用**而不是复制（`tests/ui/privacy-consumers.test.ts:75` 自动发现消费方）。改动 `privacy.ts` 的导出句会让 `tests/app/privacy.test.ts` 里的**整句哈希**失效，必须同轮重钉。
7. **临时件只放 `.superpowers/<任务>/`**（已 gitignore，`.gitignore:3`）。不要放进 `tests/**`，也不要放仓库根。
8. **提交纪律**：一个任务一个提交，`git add` 写显式路径（不用 `-A`）；提交信息写清**那一刻实测**的门禁数字；推送只在用户明确指示后做。
9. **文字风格**：任何文本不用表情符号，不用营销腔，数字必须自测并交代方法（`AGENTS.md`）。本仓既有的 `→` `⇒` `≥` `×` `#` 可以继续用。
10. **红线文件不动**：`src/ui/render.ts`、`src/ui/render-net.ts`、`src/ui/styles.css`、`src/ui/effects/**`、`src/ui/gen3-control.ts`、`src/ui/fx-gen2.ts`、`src/ui/fx-gen3*.ts`。
11. **`src/main.ts` 是结构敏感文件**：它已有 **8 处 `driver.submit(`** 与逐字保留的 net 分支（G4 T4 结论）。涉及它的任务必须走**最小侵入**，并在计划里点名改了哪几处。

13. **变异证据的"零用例"陷阱（G5 新增纪律，T1 踩过）**：审查或产出变异证据时**不许只看退出码**。必须同时看到 ① `RUN vX <root>` 的 root 是镜像；② **收集到的用例数 N > 0**；③ 干净世界那一轮 N > 0 且全绿。
    - 原因：镜像配置里的 `include` 是**相对 `test.root`** 解析的。若镜像里没有那个目录，vitest 会以 `No test files found` 退 1 —— 于是"缺陷复现"与"什么都没跑"在退出码上**完全同形**。这是本仓"0 tests look green 有四个入口"的第五个变体：**0 tests look RED**。
    - CLI 的位置参数只是在 `include` 收上来的集合上做**过滤**，救不了空 `include`（T1 的判据跑与探针跑两半都空过，已实测）。
    - 处置：夹具必须解析 vitest 输出，把"零用例 / `No test files found`"当**硬错误**判这次变异无效，并把 root 与**收集用例数**一起写进结果。
    - **探针的输入必须真的落在被变异的那条路径上**（T1 的 M1 踩过）：像"对调第 1 步与第 2 步"这种变异，只有当输入**同时违反第 1 步与第 2 步**时才可观测。T1 原来的测例构造的是"版本不符 + 玩家位已满"（违反的是第 1 与第 3 步），对调 1↔2 前后返回值**相同** ⇒ 探针在两个世界里**都全绿**（实测：变异在位 24 passed，干净世界也全绿）。同一轮里判据那一面反而是有牙的（`2 failed | 35 passed`，红的正是"四条两两组合全试一遍"那条腿）。
    - 处置：探针按**相邻对**逐一构造输入（违反 1&2 ⇒ 期望第 1 条；违反 2&3 ⇒ 期望第 2 条；违反 3&4 ⇒ 期望第 3 条），这样对任何相邻对调都敏感。收尾报告里逐条写明探针**红在哪条腿**、判据面与探针面各自的**收集用例数**；若某一面是绿的，就直说这次变异**没能被那一面复现**，不要写成通过。
    - **镜像基线必须每批从当前源码重建**（T1 的第二处踩坑）：T1 的 `mutate.mjs` 写的是 `if (!existsSync(backup)) writeFileSync(backup, before)` —— 备份**只在首次创建**。于是它在 21:25 重构 `src/net/protocol.ts`（700 → 708 行）之后，`--restore` 把**重构前**的 700 行版本灌回镜像，后续变异就跑在一个**不是要交付的版本**上（实测：共享树 708 行 / `FAF14986…`，镜像与 `.orig` 都是 700 行 / `ABDEA4DF…`）。证据是真的，但描述的是另一棵树 —— 与本仓"跑了一棵不同的树"是同一族。
    - 处置：每批变异开始前**重建镜像**（重跑 `build-mirror.mjs`），或让 `--restore` 检测 `sha256(<id>.orig) !== sha256(共享树同名文件)` 就**大声拒绝、要求重建**（别静默把旧内容当基线）。收尾报告里要附**共享树当前源码的 SHA256**，好确认证据对的是哪个版本。
    - **每一批的证据必须落到不可变目录**（T1 第二轮暴露）：`out/out-M?-*.txt` 这种**单一可覆盖槽位**会被下一批原地重写，于是**事后无法核验** —— 核 T1 时就撞上过：读到的 `mutate-run.json`（21:28:28 批）与已被 21:29 批覆盖的 `out-M2-probe-clean.txt` 拼在一起，得出"67 passed 却记 exit 1"的**假矛盾**，差点误报夹具的退出码有错。处置：每批写进 `out/run-<时间戳>/`，并在**批前与批后各取一次**那三份冻结哈希（源码 + 两个测试文件）；两者不同就判该批**作废**并大声报错。这同时堵住"跑批期间还在改文件"的竞态 —— 21:28 那批 M2 的干净世界红过一次，很可能就是它。
    - **相对 import 的 `../` 层数不许越出镜像根**（T1 阶段一评审实测，是评审人自己踩的）：vitest 把以 `../` 开头的说明符当成**从 root 起算**。镜像根是 `mirror/`、探针在 `mirror/probes/` 时写 `'../../../src/net/protocol'` 会**逃出镜像、静默读到共享树的干净源码**，于是"该红不红、全绿"。
      抓法：往**镜像那份**源码插一个只在镜像里存在的 marker，用探针打印 —— 读到 `undefined` 就是读错了树（评审人实测 `VIA_RELATIVE=undefined` / `VIA_FILE=FROM-MIRROR`）。
      ⇒ **光看输出头部的 `RUN vX <root>` 是镜像，不足以证明被测的是镜像那份源码**；`rootOk` 要从 vitest JSON 结果里的**文件绝对路径**判，不要只看退出码或头部。
    - **"覆盖面 / 完整性"型的自证必须从样本反推，不许手写清单**（T1 阶段一评审唯一的实质发现）：T1 的 `REAL_FILE_REQUIRED` 是一张手写清单，评审人自造 M5（往禁项表加一条**没有真文件样本**的新禁项）⇒ **判据面 37 条 + 探针面 24 条全绿**。也就是说"忘了同步真文件样本"今天**没有任何机制会提醒**，是必然漏而不是概率漏。
      处置：让"表里的标签集合"与"样本实际打中的标签集合 ∪ 显式豁免集"相等，这样**加标签与删标签都会红**。凡是要写"这张表必须覆盖哪些名字"的地方，都按这条做。
      顺带一条同族：T1 里那条"反向断言"（把命中过滤到 `timer.ts` 再查浏览器 API）**恒真** —— 它注释说防"报了一堆式假绿"，实际不防。写防御性断言前先问一句："它在什么世界里会红？"
    - **"能取零偏移"的变异是掷硬币，不是变异**（T2 阶段二复验实测）：评审人原来的 M4（`Math.floor(Date.now()/10000)%2`）在"窗口落进偶数桶"时偏移正好是 **0** ⇒ 被测行为与干净世界**逐字相同**、行为腿全绿。那次"没红"不代表判据没牙，而是那一轮变异**什么都没扰动**；它改用 `1 + …%2` 保证非零偏移后，三条腿稳定变红。
      ⇒ 凡是靠"加减一个取自环境的量"制造差异的变异，**先证明那个量在当前语料下非零**，否则你量到的是掷硬币。同族：变异幅度小于判据容差、或改在判据根本不读的字段上，都属于"没扰动"而不是"有牙"。

14. **纯度守卫的匹配口径，以及四条本机/本仓事实**（T1/T2/T3 都撞过）：
    - **守卫是"裸词面"匹配，且只剥注释、不剥字符串字面量**（`tests/ui/source-text.ts` 的 `stripComments` 头注自己写着这一点）。⇒ 一句**给玩家看的报错文案**里如果写了 `crypto.subtle` 这类词，守卫照样红。T3 就踩了这个：它的报错文案里写了"哈希 API（crypto.subtle 封装）"，`src/net/session.ts` 当场被"浏览器 API 零命中"那条腿打红 —— 而它**从未**真的调用过 crypto（`HashLike` 只是接口，实现由调用方注入）。
      处置：纯层里连**字符串**都不要出现这些词（改成"哈希 API"这类说法）；要断言"确实没有调用"时，判据得看**代码位有没有调用**，而不是"这个词有没有出现"。
    - **`fs.cpSync(..., { recursive: true })` 会把 Node 进程直接打崩**：本机 Node v22 上 exit `-1073740791`（0xC0000409），**无 stdout/stderr**，三家全撞过。镜像复制请手写 `readdirSync` + `statSync` 递归，或用别的办法（T3 改用了 PowerShell 的 `Copy-Item -Recurse`）。
    - **vitest 4.1.11 在 Windows 上把 `include` 写成绝对路径会匹配不到任何文件**（`No test files found`，退 1）⇒ `include` 一律写**相对 `test.root`** 的说明符。这与"零用例假红"是同一个坑的另一面：退 1 与"真红"在退出码上同形。
    - **清表情符号之前先读 `AGENTS.md` 的排版符号白名单**（这条是协调者自己踩的）：剥离脚本的字符类写成 `[\u2600-\u27BF\u2B00-\u2BFF\uFE0F]`，而 `★`（U+2605）**落在 2600-27BF 里** ⇒ 一次误删了 14 个**合法**的 `★`（`★` `→` `⇒` `↔` `←` `≥` `×` `#` 都是本仓既有约定，不在禁用之列）。已从提交里恢复，并只用"AGENTS.md 逐字点名的那一类"重删。
    - **`--restore` 的备份跨阶段会静默换掉判据**（T3 阶段二复验人自己踩的）：它的 `--restore` 从 `bak/*.orig` 灌回，而那份 `.orig` 是**上一阶段**写的旧判据文件 ⇒ 后来那批变异**实际跑在旧判据上**（收集用例数 33 变 31）。两个独立信号才抓到：① 收集数变化；② 失败信息里出现**当前源码已不存在**的断言文本。⇒ `--restore` 应从**共享树**重取，而不是从旧备份。**同族**：`exit≠0` 但"0 条失败用例"、或某个文件 `(0 test)`，都属硬错误 —— 套件级抛错（例如在 `describe` 作用域里抛）会表现成"没有失败用例却退 1"。

| CDP（`--remote-debugging-port` + Node 自带 `WebSocket`） | **能**，exit 0，完整走完 offer/answer → ICE `checking`→`connected` → DTLS → 数据通道 → ping/pong，约 5.0 秒 |
| 两个独立 Chrome 进程之间 | **能连通**。host `done=true` / `conn=connected`，guest `gotPing/gotPong=true`；真正 ICE+DTLS+SCTP 约 470ms，前面约 5.4 秒是冷启动 + 首次 `createOffer` 开销 |
| mDNS 混淆 | **默认开启**。出厂候选是 `15344d9b-….local 63625 typ host`；加 `--disable-features=WebRtcHideLocalIpsWithMdns` 后变成 `10.37.224.157 61979 typ host` |

⇒ 传输层的浏览器真值必须新建一条 **CDP 驱动线**（T9）。跨网络 NAT 打洞、跨机 mDNS 解析、丢包与切网**在这里验不了**，属 §7 用户验收。

### 3.7 文案与隐私的既有约束

- `src/app/privacy.ts` 里**已经有**面向玩家的信令句，且被整句哈希钉住；`tests/ui/privacy-consumers.test.ts:75` 会自动发现 `privacy.ts` 导出面的消费方。⇒ G5 新增的联机文案若与既有导出句重合，守卫会红；反之若要让玩家看到"默认不连任何信令服务"，**必须改 `privacy.ts` 并同轮重钉哈希**。
- 设计稿 §5.9（`:535-543`）的隐私表要求如实说明：信令服务能看到房间码/IP/连接时刻；TURN 中继若启用需写清"转发的是端到端加密后的包、看不到内容、不存储"。

## §4 裁决（D1-D25、D27、D28；D26 见编号说明）

每条给**结论 / 理由 / 代价**。有 `待裁决` 标记的见 §8。

### D1 行动同步用**锁步**，不是"主机权威"（`待裁决`的只有信令一支，这条已由设计稿定下）

- 结论：两端都跑引擎，只交换操作指令；主机**只**在"种子与硬币的所有权 / 会话身份 / 重连凭据"这三件事上是权威。
- 理由：裁决 #7（`:37`）明确选锁步；红线 2（`:47`）禁止服务端权威校验；`:56` 还补了一句"采用锁步后两端都跑引擎，比'只有主机跑'更省力"。
- 代价：任何一端算错都会分叉，且**没有第三方裁决**。缓解：每步之后比对状态指纹，不一致就停下来给可读提示（不静默继续）。这是信任制的必然代价（裁决 #2，`:32`）。

### D2 `sessionId` 只住会话层，**不进 `MatchFile`**

- 结论：主机在内存里持一张 `sessionId -> 对局` 的表；`MatchFile` 的格式与版本**不动**。
- 理由：设计稿 §5.2（`:451`）把它定义为"本局唯一 id，重连时用它找回"，是会话作用域的凭据；而 §5.5（`:500`）已经写明"主机关闭页面 ⇒ 对局结束"。放进档案会触发一次格式迁移（`MATCH_FILE_VERSION` 是 v1，`parseMatchFile` 带 `migrate` 链），并牵动 G3 的档案往返腿与守卫——为一个会话作用域的值付这个代价不值得。
- 代价：主机刷新即丢（与设计稿一致，不算退化）。

### D3 掷硬币的选面者必须是**加入方**，且**不写任何公平承诺**

- 结论：联机流程里由加入方（后进房的一方）承担选面，其 `commit-face` 必须先于房主的 `reveal-seed`。玩家文案里**不出现**"公平 / 无法作弊"这类承诺。
- 理由：硬币是种子的纯函数（`src/ui/home.ts:394` 只吃 `seed`），而种子与 salt 都由房主自己选（`src/ui/match-seed.ts:5`、`showCoin()` `src/main.ts:1100-1102`）。因此 §5.3 的 `commit{hash(seed+salt)}` 只能钉住"房主**事后**不能换洗牌结果"，**钉不住房主事前磨种子**——它可以离线生成一批种子，挑出对自己有利的那个再承诺，没有外部随机源能约束它。设计稿 `:479-483` 那条顺序约束**只在选面者是加入方时**才真的堵住这个洞（房主看不到 `face`，只有哈希）。
- 代价：与现有热座页"玩家一选面"的写法不同（`src/ui/home.ts:364-371` 与文案 `:341-345`），联机分支要显式指定选面者。另外要接受：即便照做，**房主仍可磨种子**（裁决 #2 `:32` 的信任制本来就不防作弊），所以文档与文案都不得暗示公平。
- 既有守卫（不要撞坏）：硬币到先后手的语义已被 `tests/state/coin-order.test.ts` 的 4 条腿钉住——`draftRoundOwner` 的 1-2-2-1 相对展开、默认 `createGame()` 兼容旧行为、以及 `draftStarter=0` / `=1` 两种情形下谁先选协议谁先出牌。联机分支**必须**喂给 `createGame` 一个与这四条语义一致的 `draftStarter`（`src/main.ts:1107-1113` 现在就是这么算的：`firstToPlay = 1 - starter`），**不得**为了联机去改这四条腿。

### D4 `forfeit` 只定消息，引擎动作留 G6

- 结论：`src/net/protocol.ts` 里定义 `forfeit` 消息类型与"收到即双方结束、留在档案里的是什么"这一收尾语义；**不碰 `src/core`**。
- 理由：裁决 #12（`:42`）把它绑在 §14.7（回合计时）上，而回合计时是 G6。
- 代价：G5 的投降只对"人主动点"有效，不含"超时判负"那一支。

### D5 观战只到握手为止：接受 `role`，明确回绝

- 结论：握手接受 `role: 'player' | 'spectator'`（设计稿 `:450` 的形状），但收到 `spectator` 时回一个**可读原因的拒绝**（例如 `unsupported`），真正的观战通道留给 G7。
- 理由：G5 的边界是两人对局（裁决 #5，`:35`）；留一个"半通不通"的观战入口比明确拒绝更糟。
- 代价：协议里出现一个 G5 从不放行的合法值，需要在守卫里写清"这是有意的"。

### D6 传输抽象 = 注入接口；浏览器实现是唯一出处

- 结论：`src/net/transport.ts` 声明接口（打开 / 发送 / 关闭 / 收到 / 状态变化），`src/ui/net-browser.ts` 是唯一碰 `RTCPeerConnection` / `WebSocket` / `window` 的文件，由 `src/main.ts` 注入。
- 理由：§3.2 的三对先例（`FileIoCapabilities`、`KeyValueStore`、`Ticker`）已经把这个形状定死；`tests/app-purity.test.ts` 的生成式守卫会替我们看着纯层。
- 代价：多一层间接；测试用的 fake 传输要自己维护（T2）。

### D7 纯层住在 `src/net/**`，分层变成 `ui → net → app → core`

- 结论：按目标与设计稿 §5 的标题，纯协议/会话/驱动放 `src/net/**`；它**可以** import `src/app`（`MatchFile`、`MatchDriver`、`applyRecordedAction`）与 `src/core`，**不得** import `src/ui`。
- 理由：目标明确要求 `src/net`；而 `NetDriver` 必须实现 `src/app/match-driver.ts:105` 的 `MatchDriver`、重连必须复用 `applyRecordedAction`，所以 `net → app` 是真实且必要的依赖方向。
- 代价：需要新增一份覆盖 `src/net/**` 的纯度守卫（T1），并把它写进已有的分层叙事（原先只有 `ui → app → core` 一条）。

### D8 重连凭据 = 主机内存里的当前 `MatchFile`；窗口 300s；超窗**不自动结束**

- 结论：主机持有 `lastSeenAt`；断线时 `peerStatus().online = false`、**不推进回合**；从机用同房间码 + `hello{sessionId, resuming:true}` 回来 → 主机回 `resync-res{MatchFile}` → 从机用 D9 的函数追平。超窗默认继续等待，由玩家决定是否结束。
- 理由：设计稿 §5.5 的表（`:492-507`）逐行如此；`MatchFileRecorder.actions()`（`src/app/match-file.ts:516`）与 `setupFromState`（`:472`）让"中途产出档案"不需要新机制。
- 代价：主机内存里要一直留着一份可序列化的当前档案；断线宽限与回合计时是**两套独立计时**（`:507`），后者属 G6，G5 只保证"断线不推进回合"。
- **补充裁决（2026-09-18，T6 任务书核对代码时发现）**：`src/net` 是纯层、**不许读时钟**（§2 第 2 条），
  所以 300s 窗口在实现上只能落成"**注入一个最小时钟能力**（`now(): number`）+ 宿主持有 `lastSeenAt`、
  每次收到对端消息就更新"。窗口边界口径取 **`now() - lastSeenAt > 300_000` 算超窗**（等于窗口算在窗口内，
  与"默认继续等待"同向）。这条路径原计划没写，现予认可。

### D9 新增**单一出处**的 `stateAtStep(f, n)`，不许另写 ActionRecord 映射

- 结论：在 `src/app/match-replay.ts` 追加一个具名函数，内部**只**用 `stateAfterDraft(f)` + 逐条 `applyRecordedAction(s, a)`；`n` 的边界（0 / 越界 / 满）要明确。
- 理由：§3.5 第 1 条——今天没有这个函数，而重连需要它；G4 T1 刚刚把"ActionRecord → 引擎调用"收口成唯一出处，重连不能另开一份。
- 代价：越出 `src/net/**` 的文件边界（改 `src/app/match-replay.ts`）。这是本阶段唯一一处对 `src/app` 的既有文件追加，必须在提交信息里点名。

### D10 浏览器夹具：**新增 CDP 驱动线**，不改造第五道门

- 结论：新建 `tools/browser-truth-cdp.mjs`（零依赖，Node 自带 `WebSocket`/`fetch`），采用"两个独立 Chrome 进程 + Node 当信令中继"的配方（§3.6 实测可行）。第五道门原样保留。
- 理由：`--dump-dom` **结构上**跑不完异步 WebRTC（§3.6 实测：两种预算下真实墙钟都被卡在约 5 秒）。改造第五道门会同时动摇 G1-G4 已有的 110 条判据；另立一条线风险小得多。
- 代价：多一个工具、多一套退出码与自证纪律；每条传输判据的时间预算要按"每对端至少 20 秒"给（冷启动 5.4 秒是实测值）。收益：它还能顺手解开 G4 收口文档 §3 里"主页导入 → 重放没有机器真值"那个遗留缺口。

### D11 心跳通道 `beat` 只做在线状态，不做表情

- 结论：按设计稿 §5.4（`:485-490`）建两条通道（`act` reliable+ordered、`beat` unreliable+unordered），但 G5 只用 `beat` 传心跳与在线状态。
- 理由：在线状态是"断线提示"与"重连判据"的前提；表情是纯装饰，不在 G5 目标里。
- 代价：`beat` 的"不可靠"特性在 G5 里其实用不满（心跳丢一两个无所谓），要等到 G7 观战才真正需要。
- **实测（G5 勘察，命令 `node tools/browser-truth-cdp.mjs --scenario disconnect`）**：**杀掉对端进程**后，宿主靠 `connectionState` 自己发现用了 **6339ms**（每 400ms 采样一次，第 16 次采到 `disconnected`）。
  但这个数字测的是"**进程死亡、socket 被关掉**"——操作系统会发 RST/FIN，对端能很快察觉；而**拔网线那种静默断网**不会有任何包通知对端，只能靠 ICE 的 consent freshness 超时，耗时**未验证**（RFC 7675 的上限是 30 秒量级）。
  ⇒ 结论：`connectionState` 可以当"进程没了"的快信号（约 6 秒），但**不能只靠它判在线**；`beat` 心跳是必需的。这条实测正好支撑本裁决，而不是推翻它。

### D12 房间码：6 位 Crockford Base32 剔 `I/L/O/U`，字符表与归一化只有一处

- 结论：`roomCode()` / `normalizeRoomCode()` 放 `src/net/protocol.ts`，字符表是唯一出处；输入大小写归一、剔除混淆字符后必须恰好 6 位，否则给可读原因。
- 理由：设计稿 §5.1（`:438`）与裁决 #3（`:59`）。
- 代价：无。注意"房间码不入库"（`:59`）意味着它只是频道名，**不能**用它找回对局。

### D13 校验顺序照抄设计稿，且顺序本身要被判据钉住

- 结论：`protoVersion` → `cardDataHash` → 玩家位已满 → 观战位已满（设计稿 `:460-465`），每条都给可读原因。
- 理由：顺序决定了玩家看到哪条提示（版本不一致比"位满"更该先说）。
- 补充（本次实测发现）：第 2 条要比对的指纹**只有一处出处**——`src/app/card-data-hash.ts` 导出的 `CARD_DATA_HASH`，`MatchFile` 已经在用它（`src/main.ts:446`）。T1/T3 必须引用它，不许自己拼一个哈希。
- 代价：无。

### D14 `iceServers` 从设置读，默认只给公共 STUN，**不内置任何中继**；邀请码兜底是必需功能

- 结论：设置里留 TURN 的 URL / 用户名 / 凭据三项；邀请码（压缩后的 SDP + ICE + 种子承诺）走剪贴板/任意渠道粘贴，**必须实现**。
- 理由：设计稿 §5.7（`:518-526`）把邀请码写成"可达性兜底，**不是可选功能**"；§5.8（`:528-533`）要求 TURN 可配置且不内置；裁决 #8（`:38`）"先留 TURN 接口，暂不投入中继成本"。§3.6 实测的 mDNS 混淆（对端默认只看到 `.local` 名）进一步说明直连不是必然成功。
- 代价：邀请码要做压缩与粘贴两条 UI 路（且长字符串的可用性只能靠人试）；启用 TURN 时要同步改 `privacy.ts` 并重钉哈希（§3.7）。

### D15 承诺哈希是**注入能力**，状态机保持同步

- 结论：`src/net/session.ts` 只接受"已经算好的哈希"作为输入，自己不算哈希；真实哈希由 `src/ui/net-browser.ts` 用 `crypto.subtle` 算好再喂进来。测试用确定性的替身。
- 理由：`crypto` 属浏览器 API，纯层禁用（§2 第 2 条）；而 `crypto.subtle.digest` 是异步的，若让状态机自己调，状态机会被迫变成异步，**"`seed` 不得早于 `commit-face`"这条唯一可机器判定的安全属性就锁进异步时序里、难测**。
- 代价：多一个注入点；调用方要在正确的时刻算哈希（顺序约束因此是"调用方的义务 + 状态机的守卫"两层，两层都要有腿）。

### D16 `SubmitRefusal` 新增 `'offline'`，**不复用** `'read-only'`

- 结论：T5 给 `src/app/match-driver.ts:97` 的 `SubmitRefusal` 加第五个值 `'offline'`（掉线/对端不可达时 `submit` 的拒绝码）。`'read-only'` 的原义**一个字不改** —— 它按 `:93-95` 的既有文档就是"**`dispose()` 之后的任何 `submit`**"。
- 理由：我起草计划时 T5 判据 2 写的是"断线时被拒（`'read-only'`）"，那会让同一个值承载两个含义（"这局结束了" vs "对端暂时不在"）。本仓恰好为这种事吃过**阻断级**修复：`ReplayCursor` 的 `error` 与 `diagnostic` 曾经共用一个字段，看门狗一触发就把整个驱动砖化（`src/app/match-driver.ts:144-153` 留着这段记录）。语义分开是这里的既有取向。
- 实测（本次核过）：`SubmitRefusal` 只在 `src/app/match-driver.ts` 里被定义与使用，**没有任何测试枚举这个 union**；`'read-only'` 在测试里只出现一次（`tests/app/match-driver.test.ts:1265`，断言 dispose 之后 submit）。所以加一个值**不会撞坏任何既有腿**。
- 代价：这是本阶段**第二处**越出 `src/net` 改 `src/app` 既有文件的改动（第一处是 D9 的 `match-replay.ts`）。T5 的提交信息必须点名它，并且要保留 `:93-95` 那段关于 `'read-only'` 的说明（只增不改），同时为 `'offline'` 补上它自己的文档。

### D17 邀请码的三种呈现形态（**用户已定**：二维码 / 数字 / 链接）

- 结论：三种形态都要，但它们**对应两条不同的机制**，实现上不要混为一谈。
  | 形态 | 对应机制 | 依赖 | 成本与风险 |
  |---|---|---|---|
  | **链接** | 邀请码兜底（§5.7） | 无（不依赖信令端点） | **最低**：载荷放进 URL 的 **fragment**（`#invite=<base64url>`）。按浏览器规范 fragment **不会发给任何服务器** ⇒ 比现状更符合"没有后端、不存数据"。收方点开即建房，页面读完 fragment 立刻 `history.replaceState` 清掉地址栏 |
  | **二维码** | 邀请码兜底（同一条载荷） | 无 | 容量够（实测载荷约 743 字，远在 QR 上限内）。但生成要么引第三方库（破裁决 #12 的零依赖），要么**自己写一个最小 QR 编码器** ⇒ 独立工作量，且**识别率未验证**。建议作为独立任务排在 T7 之后 |
  | **数字/短码** | **房间码**（§5.1，不是第三种编码） | **需要配置信令端点**（§8.1 方案 2） | 没有端点时它无从传递那 743 字载荷 —— "输 6 位码"与"粘一长串"是两条不同的路。字符表默认 6 位 Crockford Base32（字母数字混合） |
- 关于"数字"的字符表 —— **已定（用户 2026-09-17 拍板）：保持 6 位 Crockford Base32（字母数字混合，剔 I/L/O/U）**。
  ⇒ **D12 不动、字符表不动**，T7 不需要为"纯数字"做任何额外工作；"数字/短码"这一形态在实现上**就是既有的房间码**，
  唯一的差别是它只在配了信令端点时才可用（见上表）。撞码兜底沿用设计稿 —— 频道内已有对局时房主回 `busy`。
- 理由：把"链接/二维码"（无端点也能用，属可达性兜底）与"短码"（有端点才可用，属便利路径）分开，才不会出现"以为输个数字就能连上，其实没配端点"这种玩家侧的死胡同。
- 代价：T7 要多做两件事 —— 链接的解析与清理（含把载荷从地址栏抹掉）、以及短码入口在**没配端点时必须给出可读提示并引导到邀请码**（而不是给一个点了没反应的输入框）。二维码若要做，另开任务。

### D18 `init()` 的语义边界：它只保证**本侧**链路起来，**不能**用来判对端在线

- 结论：`NetTransport.init()` 的 `ok` 只表示"本侧链路已建立"，**不表示对端可达**。对端是否在线，只能由 `onStatus` 的状态转移与握手结果判断。**T6/T7 不许用 `init().ok` 当"对端在线"的读数。**
- 理由：T2 阶段二复验实测 —— fake 传输在 `init()` 时刻就能知道对端在不在（它是一张内存表），所以"对端不可达 ⇒ `init` 失败"这条规则在 fake 上可兑现；但**真 WebRTC 做不到**：`RTCPeerConnection` 刚建起来时还没协商，对端在不在要等 ICE / DTLS / 握手之后才知道。若 T6 用 `init().ok` 判"对端在线"，**fake 上绿、真实现兑现不了** —— 那是"测量装置比被测对象更强"的假绿。
- 代价：`fake-transport` 里那条护栏（对端不可达 ⇒ `init` 失败）**保留**（本地开发与判据都需要它），但必须同时在 `transport.ts` 的 `init` 文档里写明"这不是对端在线性的判据"，并让 T7 的实现只等本侧就绪。

### D25 加入方**不许**先出自己的 offer（T8-E 真浏览器诊断出来的设计裁决）

来源：`tools/browser-truth-lobby-cdp.mjs` 的真浏览器验收 + 两次只读诊断
（`.superpowers/g5-T8/T8E-ICE-IDENTITY.md` 与 `T8E-ICE-CONFIG.md`）。

**事实**（同一 headless Chrome、同一会话的对照）：
- **房主**那条连接：`gathering = complete`、拿到 **2 条候选**（1 host + 1 srflx）。
- **加入方**那条（每个 Chrome 里**只有一条**，而且就挂着 `[act,beat]` 通道）：**40 秒仍是 `gathering`、候选 0、
  `onicecandidate` 一次都没触发**。它的配置**干净**（`iceTransportPolicy:"all"`、只有两条 Google STUN、无 TURN）、
  四次描述调用**全部 ok=true**、**零 `icecandidateerror`**、对端 offer 完好（`ufrag` + 2 条候选）。
- 时间线上决定性的一步：加入方**先** `setLocalDescription(offer)`（自己的 offer），随后收到对端 offer
  ⇒ `sig->stable` → `have-remote-offer` → **`gather->new`**，此后 40 秒**再无任何事件**，`iceConnectionState` 始终 `new`。
- **对照实验**（同一 headless Chrome、只读）：干净顺序（对端**没有**本地 offer）/ 应用侧 glare / 边收集边喂 remote
  —— **三种都 complete 且都有候选**。

⇒ **裁决**：这是 **Chrome 在"本地 offer 被回滚、同一条 PC 转成 answerer"这条路上不重启候选收集**，
**不是本仓某一行写错**。绕开的唯一方向是**设计**：**加入方的传输在收到对端 offer 之前不许创建自己的 offer**
（候选路径：`init()` 按角色分流 —— 房主才 `createOffer`；加入方只建通道与监听，等 `acceptOffer` 应用对端 offer 后
再 `createAnswer`）。**代价**：要动 `src/ui/net-browser.ts` 的 `init()`（T7 的交付物）与 `NetTransport` 的既有形状，
需先判定"加入方能否在不 init 出 offer 的前提下把本侧链路准备好" ⇒ **这不是"一行级"修复**，本轮**不做**。

**影响面（今天的最终状态）**：`browser-truth-lobby-cdp.mjs` 的判定 ②（加入方产出回示码）与 ③（握手推进）

（那条 `hello` 一直停在待发位上）。⇒ **"两台设备真能开局"今天不成立**，卡在 D25 这条设计约束上。

**后续（2026-09-19 补注）**：D25 那条设计裁决**已在 T8 修复轮落地** —— `NetTransport` 的
`TransportInit` 长出 `role?: 'host' | 'guest'`，`init()` 按角色分流（只有房主 `createOffer`，加入方

### D27 硬币屏插进握手：保留"叫面早于公开种子"（**用户 2026-09-19 裁决**）

### 8.3 邀请码的形态 —— **已定：三种形态都要，见 D17**（长度已实测）

用户 2026-09-17 拍板：**二维码、数字、链接三种形态都做**。三者对应的机制不同（链接与二维码走"邀请码兜底"、
无端点也能用；数字/短码走"房间码"、**必须有信令端点**），映射关系、成本与风险写在 **D17**。
下面的实测长度仍然是这三条的共同前提。

设计稿只说"压缩后的 SDP + ICE + 种子承诺"（`:522`），没说长度上限与呈现方式。本次实测（方法：一个真 Chrome 造 non-trickle offer、等 `iceGatheringState === 'complete'` 再量；命令与原始输出见 `.superpowers/g5-recon/FINDINGS.md` 第 6 节）：

| 量 | 出厂（mDNS 混淆开启） | 对照（`--no-mdns`） |
|---|---|---|
| SDP 原文 | 587 字 | 566 字 |
| SDP 的 base64 | 784 字 | 756 字 |
| `deflate-raw` 后 | 431 字节（压缩比 **0.734**） | 404 字节（0.714） |
| `deflate-raw` + URL-safe base64 | 575 字 | 539 字 |
| 再加种子承诺与选面承诺（两个 64 位十六进制串 + 结构开销约 40） | **约 743 字** | 约 707 字 |

两条结论：

1. **`CompressionStream('deflate-raw')` 在 Chrome 里可用**（实测 `hasCompressionStream: true`），所以压缩不需要任何第三方库，裁决 #12 的零依赖守得住。但它对 SDP 只能压到约 **0.73**——SDP 里大段是 ICE 凭据与 UUID，本来就近随机，指望"压得很小"是不现实的。
2. 实际邀请码是**约 700 到 750 字**：**能粘贴、不能手打**。另外本次环境只产生 **1 个候选**（无 STUN、网卡单一），真实机器配上公共 STUN 后通常会有 host + srflx（可能还有 IPv6）若干候选，邀请码大概会涨到 **1KB 上下**——**这一条是推断，未实测**。

所以要你拍的是：

- 接受"每局粘贴一次约 750 到 1000 字的字符串"吗？如果觉得烦，那 §8.1 的方案 2 就该当主力（配了端点就能输 6 位码），邀请码只作兜底——这也正是设计稿 §5.7 给它的定位。
- 要不要二维码？**容量**不成问题（750 字远在 QR 上限内），但生成与识别通常要引第三方库；自己写一个最小 QR 编码器是独立工作量，且**识别率未验证**。

## §9 风险与已知缺口

1. **跨网络可达性在本机无法验**（§3.6 实测只能到"同机两个进程"）。NAT 打洞、跨机 mDNS 解析、丢包与切网全在 §7。
